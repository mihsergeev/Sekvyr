# Приложение в Docker: `.env` из панели

[English version](app-docker.md)

Задача простая: приложение на сервере поднимается через `docker compose`, а
переменные для него лежат в панели. Правим значение в вебе - контейнер
подхватывает его сам, без похода на сервер.

Ниже пошагово то, что проверено на живом сервере.

## Что получится

```
панель  --HTTPS-->  агент на сервере  -->  /run/sekvyr/shop.env  -->  docker compose
                         |                                               ^
                         +-- после изменения выполняет ------------------+
                                    docker compose up -d
```

Файл со значениями лежит в `tmpfs` (`/run`): перезапуск и обновление агента он
переживает, а перезагрузку и остановку службы нет.
Единственная копия на диске - собственная копия агента, зашифрованная ключом
ноды (см. ниже). Агент проверяет панель раз в минуту.

Агент на сервере **один**, сколько бы приложений на нем ни было. Приложения -
список в его конфиге; агент перечитывает список каждую минуту, поэтому
добавление нового ничего не перезапускает.

## 1. Заведите проект и окружение

В панели: "Новый проект", имя (например `shop`), в нем окружение `prod`.
Дальше "Добавить ключ" столько раз, сколько нужно переменных.

Многострочные значения (конфиги, ключи, сертификаты) класть можно. Значения
со знаком `$`, кавычками и переносами агент пишет так, что `docker compose`
читает их буквально и ничего внутри не подставляет.

## 2. Подключите сервер

Раздел "Серверы", "Подключить сервер", выберите проект, затем окружение. Панель
покажет одну команду с одноразовым токеном:

```sh
curl -fsSL https://ПАНЕЛЬ/api/v1/machine/install.sh | sudo sh -s -- \
  --token ТОКЕН --project shop --env prod
```

Она делает все сразу: скачивает агента в `/opt/sekvyr-agent`, меняет токен на
постоянную личность (секрет остается на сервере с правами 0600), заводит службу
`sekvyr-agent` и добавляет ей первое приложение.

Токен одноразовый и по умолчанию действует пятнадцать минут, другой срок можно
задать в том же окне.

На уже подключенном сервере установщик токен не тратит и обновляет только
бинарь: новая личность оставила бы прежнюю в панели с правами, а приложения из
`sekvyr add` пропали бы из списка. Окружение такому серверу выдается на его
странице в панели, кнопкой "Подключить приложение". Подключить сервер заново,
с новой личностью: `--reenroll`.

Галочка "Без проекта" подключает только агента: в команде нет `--project` и
`--env`, а приложения добавляются потом со страницы сервера.

Полезные ключи установщика: `--dir`, если агент нужен в другом каталоге, и
`--no-cache`, если шифрованная копия значений на диске не нужна (повторный запуск
установщика его сохраняет, вернуть копию: `--cache`). С `--no-cache` агент
удаляет и копию, оставшуюся с тех пор, когда она была включена.

Установщик и агент говорят на языке интерфейса панели, откуда взята команда: в
команде есть `--lang`, юнит получает `Environment=SEKVYR_LANG=<этот язык>`,
агент запоминает язык в конфиге, и на нем же пишут журнал службы и
`sekvyr add`. `SEKVYR_LANG` на сервере его не перебивает: установщик берет
`--lang` из команды, а `sudo` сбрасывает `SEKVYR_LANG`, и `sudo sekvyr add` его
не видит. Сменить язык службы: запустить установщик заново с `--lang ru` или
`--lang en`.

**Через прокси.** Если наружу сервер ходит только через прокси, запускайте
установщик с `HTTPS_PROXY` (и `NO_PROXY`) в окружении: через `sudo -E` или
`export` в root-шелле.

```sh
export HTTPS_PROXY=http://proxy.example.ru:3128 NO_PROXY=localhost,127.0.0.1
curl -fsSL https://ПАНЕЛЬ/api/v1/machine/install.sh | sudo -E sh -s -- \
  --token ТОКЕН --project shop --env prod
```

Установщик сохраняет эти значения для службы в `/etc/sekvyr/proxy.env` (права
0600, юнит читает его через `EnvironmentFile`). Поменять их потом: правка этого
файла и `sudo systemctl restart sekvyr-agent`.

**Без systemd** (OpenRC, supervisord, контейнер) установщик откажет еще до
подключения, и токен не потратится. Ставьте агента с `--no-service` и
запускайте `sekvyr agent --config /etc/sekvyr/agent.json` своим супервизором.
После самообновления вне systemd агент сам заменяет свой процесс новым
бинарем. Если агент работает в docker-контейнере рядом с приложением, дайте
контейнеру init (`init: true` в compose): иначе осиротевшие процессы команд
после изменения остаются зомби.

## 3. Опишите приложение

`/app/shop/compose.yml`:

```yaml
services:
  app:
    image: registry.example.ru/shop:1.4.2
    restart: unless-stopped
    # Файл пишет агент. Абсолютный путь: файл лежит в tmpfs, а не в каталоге
    # проекта.
    env_file:
      - /run/sekvyr/shop.env
```

Путь и команду агент выводит из имени проекта и ничего не спрашивает: файл
`/run/sekvyr/shop.env`, после изменения - `docker compose -f
/app/shop/compose.yml up -d`. Если compose-файл лежит в другом месте, скажите
это один раз:

```sh
sudo sekvyr add shop/prod \
  --on-change 'docker compose -f /srv/shop/docker-compose.yml up -d'
```

Файл со значениями держите в `/run/sekvyr`: служба идет с
`ProtectSystem=strict` и пишет только в свои каталоги. Если файлу правда нужно
лежать в другом месте, разрешите службе этот каталог
(`sudo systemctl edit sekvyr-agent`, дальше `[Service]` и
`ReadWritePaths=-/srv/shop`; минус - чтобы служба поднималась и без этого
каталога) и передайте `sekvyr add` ключ `-o /srv/shop/.env`.

Команда после изменения выполняется в той же песочнице: система только на
чтение, кроме каталогов из `ReadWritePaths`, домашние каталоги тоже только на
чтение (плагин docker compose и вход в реестр из `/root/.docker` видны). Если
команда пишет куда-то еще (`artisan config:cache`, `cp` в `/srv`), этот каталог
разрешают так же, строкой `ReadWritePaths=-/путь`.

## 4. Проверьте

```sh
sudo sekvyr ls                           # какие приложения обслуживаются
sudo cat /run/sekvyr/shop.env            # значения приехали
sudo docker compose -f /app/shop/compose.yml up -d
sudo docker exec shop-app-1 printenv DB_PASSWORD
```

Теперь поменяйте значение в панели и подождите минуту: `sudo journalctl -u
sekvyr-agent -n 5` покажет, что значения обновлены, а сразу следом compose
пересоздаст контейнер.

На живом сервере это заняло 38 секунд от правки до пересозданного контейнера.

## Еще одно приложение на том же сервере

Раздел "Серверы", у нужного сервера кнопка "Подключить приложение", выбрать
окружение. Панель выдаст серверу доступ на чтение и покажет команду:

```sh
sudo sekvyr add checkout/prod
```

Все. Второй службы не появляется, перезапускать нечего: агент увидит новую
строку в списке в течение минуты и напишет `/run/sekvyr/checkout.env`.

Кнопка делает два дела разом, политику доступа и команду. Раньше право
выдавали в разделе "Доступ" отдельно, и забытая политика встречала агента
отказом "этой машине окружение не выдано".

Убрать приложение: `sudo sekvyr rm checkout/prod` (файл со значениями и копия
значений этого приложения у агента тоже удаляются, чтобы никто не работал по
протухшей копии).

Путь по умолчанию выводится из имени проекта. Поэтому второе окружение того же
проекта (stage рядом с prod) или одноименный проект другой группы подключаются
со своим файлом и своей командой:

```sh
sudo sekvyr add shop/stage -o /run/sekvyr/shop-stage.env \
  --on-change 'docker compose -f /app/shop-stage/compose.yml up -d'
```

Без `-o` агент откажет: два приложения в одном файле затирали бы его друг другу
каждую минуту. Приложение из другой группы называется с группой, так же, как в
`sekvyr list`: `sudo sekvyr rm initech/frontend/prod`.

## Почему `up -d`, а не `restart`

`docker compose restart` перезапускает процесс в **том же** контейнере, а
переменные окружения задаются при его создании. Проверено: после правки
`restart` оставил приложению старое значение, `up -d` пересоздал контейнер и
подставил новое.

Поэтому по умолчанию `up -d`. Compose сам ничего не делает, если файл не
менялся, так что лишних пересозданий не будет.

## Если перезапуск не нужен

Некоторые приложения умеют перечитывать конфигурацию сами. Тогда вместо
пересоздания:

```sh
sudo sekvyr add shop/prod \
  --on-change 'docker compose -f /app/shop/compose.yml kill -s HUP app'
```

Если контейнер читает файл со значениями сам, монтируйте каталог, а не файл.
Агент заменяет файл атомарно, а смонтированный отдельно файл (bind-mount одного
файла) оставляет контейнеру старый inode. Дайте файлу свой каталог
(`-o /run/sekvyr/shop/app.env`) и монтируйте `/run/sekvyr/shop`.

А если приложение читает файл напрямую, агенту можно вообще не трогать compose:
`--on-change true` только обновляет файл, а перечитывает его сервис сам. Пустой
`--on-change` так не работает: агент подставит свое значение по умолчанию,
`docker compose ... up -d`.

Это значение по умолчанию `sekvyr add` записывает в конфиг агента
(`/etc/sekvyr/agent.json`), когда добавляет новое приложение без
`--on-change`. Приложение, у которого в конфиге `on_change` пустая или ее нет
вовсе, после обновления файла ничего не выполняет. Прежние версии считали
пустую команду за `docker compose ... up -d`, теперь нет.

Повторный `add` того же приложения не создает второй записи, а меняет в
существующей только переданные ключи: файл, команда и права, заданные раньше,
остаются как были.

Команда, которая не прошла (docker перезапускался, compose упал), повторяется,
пока не пройдет, даже если значения больше не менялись: сначала через минуту,
потом с паузой, которая удваивается до часа. Команда, исправленная через
`sekvyr add --on-change`, пробуется на следующем круге. Повтор переживает
перезапуск агента.

## Что стоит помнить

- **`env_file` держит секреты вне `compose.yml`**, а значит и вне git.
  Значения, прописанные в `environment:`, лежат в compose-файле открытым
  текстом. Внутри работающего контейнера и те и другие - обычные переменные
  окружения: их видит любой, кто может выполнить на сервере `docker inspect`.
- **Переменные переживают перезагрузку.** Docker запечатывает их в контейнер
  при создании, поэтому после ребута приложение поднимается со своими
  значениями, даже если файла еще нет. Проверено: контейнер перезапустился без
  файла и сохранил переменные.
- **Пересоздать контейнер без панели тоже можно.** Агент держит на диске
  копию последних значений (`/var/lib/sekvyr/cache*.bin`, зашифрована ключом
  ноды) и разворачивает ее, когда панель недоступна, о чем пишет в журнал
  службы. Только когда недоступна: если доступ отозван или окружения больше
  нет, копия не используется. Кому копия на диске не нужна, ставит агента с
  `--no-cache`: тогда без панели файл не появится, и пересоздание контейнера не
  пройдет.
- **Один сервер - одна личность в панели и одна служба**, сколько бы приложений
  на нем ни было. В журнале панели видно, какое окружение забирал агент. Агент
  спрашивает панель каждую минуту, но повторное чтение того же набора не
  пишется в журнал каждый раз: строка появляется на новый набор значений, новый
  адрес и раз в сутки, с числом повторов с прошлой строки.
- **Права на файл 0400, владелец root.** docker compose и systemd читают его от
  root, поэтому от какого пользователя работает приложение, неважно.
  Приложение, которое читает файл само и под другим пользователем, прочитать
  его не сможет: отдайте ему значения через compose или systemd.
- **Файл в формате docker compose, а не скрипт shell.** compose и
  `EnvironmentFile` systemd читают его в точности, а подключать его в shell
  через `source` нельзя: значение, где есть и апостроф, и обратный апостроф,
  не записать так, чтобы compose и shell прочли его одинаково, и shell
  выполнил бы то, что между обратными апострофами. Запустить процесс со
  значениями без compose можно так: `sekvyr run -- ./app`. Значения панели
  при этом перекрывают одноименные переменные, унаследованные от службы или
  образа.
- **Одноименные ключи в разных папках разрешены.** Сервер (агент, ESO,
  `/api/v1/machine/env`) получает одно значение на имя: из папки, которая идет
  позже по порядку путей (`/db` после `/`). Если серверу выдана только одна из
  этих папок, значение берется из нее. Выгрузка `.env` из панели для человека
  содержит обе строки с заголовками папок, и последняя перекрывает первую, как
  в compose.
- **В имени ключа только буквы (в том числе кириллица), цифры, `_`, точка и
  дефис**: то, что разбирает docker compose. Ключ со старым именем (например
  `smtp/host` после переноса из Vault в ранних версиях) агент пропускает с
  предупреждением, а машинная выдача `.env` его не отдает. Значение под таким
  именем не правится: ключ нужно переименовать.
- **Права по папкам действуют везде.** Запрет на папку скрывает ее ключи и из
  списка, и из того, что получают серверы. Действия над окружением целиком
  (выгрузка, все значения разом, восстановление снимка, смена родителя
  окружения) требуют права на каждую папку окружения, иначе панель отказывает с
  кодом 403 и объясняет почему.
