Каркас, CRD, Helm и авторизация

Подготовлено к рассмотрению

Создан отдельный Go-модуль оператора с запускаемым контроллером, двумя CRD, Helm chart и клиентом машинной авторизации. Защита от небезопасного применения обеспечена закрытым контуром: каркас не получает значения, не записывает прикладные Secret и не перезапускает приложения.

Контрольная точка пользователя. Работа останавливается после этапа 2. E2E2 runtime, сервис witness, синхронизация и rollout требуют следующих этапов. Выпуск 1.0.3, существующий агент и рабочие стенды этим изменением не обновлялись. Коммит, публикация образа, Helm chart или GitHub release не выполнялись.

Этот путь еще не реализован и не выдается за проверенный.
  • Runtime RBAC разрешает GET только заданных bootstrap Secret, чтение CR и запись их status. Нет list/watch Secret, создания или изменения Secret, patch Deployment, удаления Pod, scale, TokenRequest или impersonation. Lease можно обновлять только по точному имени.
  • Приложение не выбирает URL панели, ServiceAccount, target или ключи. Его CR ссылается на точное имя и UID Store и разрешенный binding. Привязка дополнительно ограничивает имя CR, источник, выборку, target и список Deployment.
  • Проверяются конфликты binding и target внутри Store и между Store, защищенные имена целей, UID bootstrap, разрешенные origins, режим E2E2/WitnessCurrent, канонические пути, NFC и запрещенные Unicode-категории. Это текущая авторизация формы; чтение существующего target, проверка его UID и durable ownership registry появятся позднее.
  • CA ConfigMap должен быть immutable, совпадать по имени/UID/key и SHA-256 набора DER-сертификатов из bootstrap. Пользовательский CA в HTTP-клиенте заменяет системные корни. Изменение CA требует новой административной авторизации.
  • Проверка Secret UID обнаруживает потерю и замену объекта. Совпадение поколения state и конфигурации не доказывает отсутствие одновременного отката всех доверенных корней. Такое обещание не дается.
  • Pod работает без root, дополнительных capabilities и повышения привилегий, с seccomp RuntimeDefault и файловой системой только для чтения. В runtime-образе отсутствуют shell и пакетный менеджер. Метрики выключены.

CRD используют структурную OpenAPI-схему и CEL для неизменяемых ссылок и важных полей, режимов шифрования, согласованности selection/rollout и уникальности bindings. Некоторые проверки путей и Unicode выполняются runtime: сложные вложенные CEL-выражения превышают бюджет API. Неизвестные поля отвергаются при fieldValidation=Strict; обычный API может предупреждать или удалять их. Они не сохраняются как скрытая конфигурация.

Авторизация без статического пароля

  1. Kubelet проецирует два отдельных токена: один для Kubernetes API, второй с audience sekvyr для панели. Оба привязаны к pod и фиксированному ServiceAccount, запрошенный срок — один час.
  2. Клиент при каждом Login заново открывает файл projected-токена. Локально проверяет форму, namespace/ServiceAccount, audience, pod binding и срок до отправки. Это проверки неаутентифицированных claims, а не проверка подписи JWT.
  3. Панель проверяет подпись, issuer, audience, срок и зарегистрированные полномочия по независимо настроенным JWKS кластера. Она выдает короткую машинную сессию. JWKS-проверка без TokenReview не узнает об удалении pod немедленно; срок токена ограничивает время его использования после кражи.
  4. HTTP-клиент принимает только разрешенный HTTPS origin, проверяет TLS, блокирует redirects и environment proxy, ограничивает размер ответов и время ожидания. Сессия остается в памяти и не экспортирует bearer-токен. Ошибки возвращают стабильные коды без upstream body, URL и учетных данных.

В Helm values содержатся только ссылки, UID и административные параметры. Ключи, пароли, JWT и содержимое trust bundle туда не передаются: Helm сохраняет values в истории релиза. Внешний bootstrap готовит администратор; генерация или замена ключа ноды оператором отсутствует.

Что остается до настоящей синхронизации

Этап 3 должен реализовать точные байты E2E2, проверку подписи publisher, AEAD, подписанной обертки read key и independently pinned trust. Затем нужны новый panel API, immutable snapshots, witness с внешним durable append-only ledger, двойная проверка актуального head, надежный checkpoint/ownership registry и атомарная запись Secret. Опциональный restart включается позднее поверх подтвержденной ревизии.

Журнал witness должен восстанавливать всю историю полномочий: genesis, publisher policies и отзывы, read-key epochs, witness epochs и recovery. Durable append предшествует commit receipt и fresh proof. Stale cache не дает права подписывать актуальный head. Пока нет реального storage adapter и проверок восстановления, устойчивость witness не считается доказанной.

Полный прикладной E2E с доставкой новых значений в pod, reload/restart приложения, недоступностью панели/witness, восстановлением ledger и ротациями еще впереди. На этом этапе проверяется безопасный отказ каркаса. Поддержка рабочего кластера и готовность к production пока не заявляются.

Файлы и воспроизведение

Исходники находятся в operator/. Архитектура и протокол — в operator/design/, установка каркаса — в operator/charts/sekvyr-operator/README.html, реальные Kubernetes проверки — в operator/tests/kind/. CI включает отдельную проверку CRD через настоящий API kind, помимо unit/schema/image checks; удаленный запуск CI еще не выполнялся. Публичные примеры содержат синтетические ссылки и не подходят для живого bootstrap.

cd operator
GOWORK=off go mod verify
GOWORK=off go vet ./...
GOWORK=off go test -count=1 ./...
CGO_ENABLED=0 GOWORK=off go build -o /tmp/sekvyr-operator ./cmd/operator
python config/generate_crds.py --check
python -m unittest discover -s tests/chart -v
helm lint charts/sekvyr-operator --namespace apps \
  -f tests/chart/values.public.example.yaml
docker build -t sekvyr-operator-stage2:local .

Изолированный Kubernetes harness создает только кластер sekvyr-stage2; он не использует текущий production context. Временный kubeconfig и bootstrap остаются вне репозитория. Запускать harness следует в локальном Linux с Docker и отдельным каталогом временных данных. WSL-поправка failCgroupV1:false ограничена тестовым кластером и не меняет конфигурацию хоста.

Первичные источники: controller-runtime v0.25.2, структурные CRD и CEL, projected ServiceAccount tokens, поведение Go HTTP client.
