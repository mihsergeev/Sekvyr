Результат испытаний · trial · этап 6

Sekvyr operator: независимый журнал, восстановление и HA fencing

Этап 6 завершен в испытательном контуре. Реализованы подписанный канонический журнал, административные ротации и восстановление checkpoint, отдельный fencer и Kubernetes admission. На реальном Kubernetes v1.34.1+k0s прошли 23 группы E2E, включая синхронизацию Secret с приложением, отказы, откат состояния, восстановление generation 2/3, смену всех ключей и настоящий CAS 409 для уже одобренной старой записи.

Профиль trial-canonical-journal-v1 проверен на одном тестовом узле. Независимость production storage и WORM, настоящий Cilium network partition и естественный failover за короткое admission window не подтверждены. Границы испытаний приведены ниже. Выпуск и production rollout не выполнялись; этап 7 не начат.

Как проходят данные и полномочия

Доверенные авторы→Панель: ciphertext→Оператор: проверка и расшифровка→Secret → приложение

Read key и ключ подписи автора не передаются панели. Приложение получает выбранные значения из Kubernetes Secret.

Панель / оператор↔Witness × 2↔JournalGateway↔S3: версии и retention

Gateway имеет storage credentials. Witness, fencer и оператор работают через ограниченный API по mTLS с отдельными полномочиями.

Lease: кандидат→Fencer × 2→Grant → все барьеры → activation→Admission → Kubernetes CAS

Grant и activation сохраняются в том же независимом каноническом журнале. Сам Lease не разрешает запись.

Профиль ограничен одной log/view и одним target Secret на установку; workload - Deployment. Namespace, ServiceAccount, Lease и все управляемые объекты заранее создает администратор и закрепляет по UID. В HA оператор не создает target Secret автоматически. Helm по умолчанию оставляет HA, sync и rollout выключенными.

Журнал и HA

Доверие начинается с независимо закрепленного подписанного genesis и минимального cursor. Чтение заново проверяет непрерывную цепочку записей, подписи, точные версии объектов и retention receipts. Mutable head не является источником полномочий. Полный record записывается в один фиксированный slot условным If-None-Match: *; счетчики journal и снимков данных различаются. Потерянный ответ разрешается только по тому же slot и точным canonical bytes, без переноса кандидата на новый cursor.

Проверка отвергает gaps, predecessor fork, лишние версии, delete markers, усеченный поток, неверный genesis, подпись или retention и откат ниже независимого cursor. Gateway не предоставляет delete, copy, multipart, unconditional PUT или произвольный S3 proxy. Испытательный backend - SeaweedFS с versioning, COMPLIANCE retention и синхронным правилом записи filer.

Fencer использует отдельный ServiceAccount. TokenReview проверяет projected JWT с audience sekvyr-fence, bound Pod UID, ServiceAccount UID и точный Lease UID. Полная holder identity фиксируется при старте процесса. Каждая повторная попытка grant CAS заново читает Lease; старый процесс не перенимает новую identity из GET.

Подписанный grant закрепляет установку, bootstrap generation, Pod UID, process identity, монотонный term, authority digest, canonical snapshot и полный набор object UID. Он становится активным только после установки и повторного чтения каждого fence-барьера и отдельной journal activation. Writer session неизменяема для конкретного reconciliation.

При каждом новом canonical head нужен новый grant и новые барьеры, в том числе при одинаковом plaintext. Барьеры меняют только metadata: Secret data, data revision и Pod template от этого не меняются. Принятый E2E2 head дополнительно сверяется с живым journal head до новой записи checkpoint или разрешения на данные.

Webhook с failurePolicy=Fail ограничен точными namespace и managed names. Обычная запись требует текущий активный grant, bound Pod, неизменный fence, fixed session hash и точные UID/resourceVersion. Admission не читает Lease и не выполняет побочных изменений. Fencer может менять только fence; оператору запрещены create/delete/apply и mutating subresources защищенных объектов. Административное исключение задается точными субъектами, без wildcard-групп.

Восстановление

  1. Администратор подготавливает новый state Secret UID, актуальные node/trust pins, подписанный enrollment и увеличенную bootstrap generation. Обычная reconciliation не сбрасывает потерянный state.
  2. Независимый администратор подписывает план с точными cursor, snapshot, UID/generations CR и Store, binding identity, target/state UID и digest ожидаемого защищенного state. План действует не более 24 часов. Первичная initialize - отдельная операция с generation 1 и отсутствующим state.json.
  3. sekvyr-checkpoint-recovery проверяет зашифрованный envelope и подписанный reader wrap. Живые journal и nonce-bound witness proofs обязательны; plaintext import и автоматическое обучение ключам из панели отсутствуют.
  4. Сначала сохраняется prepared checkpoint и новое разрешение rollout, затем проверенные target bytes через Kubernetes CAS, затем complete. До завершения обычный runtime возвращает RecoveryPending.

Повтор после потери ответа использует тот же проверенный план и уже выбранную revision; точное совпадение данных и metadata предотвращает повторную target-запись. Новый план поверх prepared state обязан подписать его точный digest. Завершенный state нельзя сбросить повторной подписью в той же generation.

Исторический pending rollout по умолчанию инвалидируется. При одинаковых выбранных bytes сохраняется data revision. Разрешить новый rollout можно только отдельным подписанным allow_rollout, разрешениями установки/CR и реальным изменением данных.

Journal GET и Kubernetes CAS выполняются раздельно. Concurrent canonical commit может временно оставить target на ранее проверенном снимке; финальная проверка оставит RecoveryPending и потребует новый рассмотренный exact-cursor план. Атомарная свежесть между двумя системами не заявляется.

Методика проверки split-brain

Один сценарий проверяет новый процесс в том же Pod, другой - передачу лидерства другой реплике при живом старом владельце. Для задержанной записи требуются реальный bound-токен, положительный ответ настоящего admission, удержание именно этого запроса по уникальной метке и resourceVersion, полная активация нового grant и окончательный ответ storage CAS 409. Таймаут, чужой фоновый запрос и пустой containerID не считаются успехом.

Пауза выполняется через runtime конкретного контейнера: Linux не доставляет SIGSTOP процессу init из того же PID namespace. Правило Linux для init в PID namespace. Отдельный worker одновременно владеет командой pause и обязательным resume; основной тест не может отправить поздний pause после завершения watchdog. Таймер после подтвержденной паузы ограничен 25 секундами, к нему добавляется задержка команд runtime; жесткий real-time предел не заявляется.

Перед управлением контейнером сверяются owner-chain и UID Kubernetes, node, container ID, PID, время старта и точная команда оператора. Если containerd сохраняет tag вместо canonical image reference, обе точные записи образов должны указывать на ожидаемый digest, raw manifest проверяется по SHA-256, а Pod imageID - по canonical reference. Произвольное совпадение имени образа не разрешает действие.

Модель сбоя в основной HA-приемке - долгая пауза прежнего владельца с уже одобренной ожидающей записью. Настоящая сетевая изоляция через Cilium отдельно не подтверждена: уникальная метка Pod не вошла в security identity и bounded preflight не заблокировал диагностическое соединение. Временная политика и метка удалены; этот вариант не считается успешной проверкой.

Границы безопасности

  • Испытательный профиль не подтверждает независимость production storage, администратора или backup-доменов. Trial Object Lock не является сертификацией физического WORM.
  • Component restart не доказывает сохранность при потере питания, отказе диска или всего узла. Несколько replicas на одном узле не создают независимые fault domains.
  • Предполагаются честный логический witness, доверенный администратор и честный Kubernetes API server с монотонными resourceVersion/CAS. Byzantine quorum и защита от компрометации текущего оператора или администратора не реализованы.
  • После нового объектного барьера уже одобренная задержанная запись старой сессии должна конфликтовать по RV. Запись до барьера может завершиться перед продвижением владельца этого объекта. Общей атомарной передачи всех объектов нет.
  • Raw etcd restore с откатом RV при сохранении уже одобренного запроса не покрывается. Не заявляются cross-system transaction, exactly-once workload restart или мгновенный отзыв выполняющейся записи.
  • При отказе gateway/journal, fencer или webhook новые защищенные записи блокируются. Уже работающее приложение сохраняет ранее полученную конфигурацию. Административный порядок восстановления webhook требует отдельной подготовки.
  • Старые бинарники могут отвергнуть новый state или authority policy. Совместимость после перехода к новым форматам отдельно не заявляется.
