Sekvyr operator: проверочная установка этапа 6

Chart 0.1.0, приложение 0.1.0-stage6-trial. Это разработка с проверяемой синхронизацией, отдельно разрешаемым Deployment rollout и экспериментальным HA fencing. Это не выпуск для эксплуатации. По умолчанию sync.enabled=false, rollout.enabled=false и ha.enabled=false: разрешены только проверка bootstrap и обновление статусов. Readiness pod означает готовность процесса, а не актуальность данных или завершение rollout.

Подготовка администратора

Выделите один namespace, ServiceAccount и идентичность панели на установку. Заранее создайте три разных Secret и запишите их настоящие UID. Chart их не создает, не принимает под управление и не удаляет.

  • Identity: неизменяемый Opaque Secret с заранее созданным ключом ноды. Ключ данных задается через identityKeySecret.key.
  • Trust: неизменяемый Opaque Secret с независимо подготовленным пакетом доверия.
  • State: заранее созданный изменяемый Opaque Secret. Ключ из stateSecret.key содержит marker с installationID и bootstrapGeneration. Для синхронизации второй ключ state.json содержит version=1, installationID, bootstrapGeneration, trustBundleUID, nodeFingerprint и пустой bindings при новой установке. Потеря или замена объекта требует административного восстановления, runtime его не создает заново.

В Helm values передаются только имена, UID, ключи данных и разрешенные HTTPS origins. Не помещайте туда приватные ключи, пароли, токены или содержимое trust bundle: Helm хранит values в истории релиза. Файл tests/chart/values.public.example.yaml содержит только фиктивные ссылки для проверки шаблонов.

Соберите образ из каталога operator/, используйте его проверенный digest в image.digest. Floating tag не принимается. Namespace из values должен совпадать с namespace релиза. Изменение авторизации требует согласованной административной конфигурации и bootstrap generation.

Внешние SA и Lease, обновление Helm

По умолчанию serviceAccount.create=true, leaderElection.create=true и ha.fencer.serviceAccount.create=true: chart создает эти ресурсы. Для заранее созданных административных ресурсов установите соответствующий create=false. Для SA оператора обязателен serviceAccount.uid, для Lease — leaderElection.uid; точное имя Lease задает leaderElection.id. В HA допустим fallback на явно заданные ha.operatorServiceAccountUID и ha.leaseUID; несовпадающие дубли запрещены. Внешний fencer SA закрепляется ha.fencer.serviceAccount.uid. Никакого lookup, определения UID по первому обращению или принятия внешнего объекта под управление Helm нет.

Generic pins попадают в installation JSON как serviceAccountUID, leaderElectionLeaseName и leaderElectionLeaseUID. Runtime проверяет их прямым GET, а имя Lease сопоставляет с аргументом процесса. При pin SA добавляется только GET точного ServiceAccount. Значения по умолчанию без pins не добавляют эти JSON-поля.

configuration.retain=true сохраняет неизменяемые ConfigMap конфигурации с аннотацией helm.sh/resource-policy: keep при upgrade/uninstall. Имена включают hash содержимого, старые pod могут безопасно дочитать прежнюю ревизию. После удаления release эти объекты остаются без управления Helm; администратор удаляет только известные UID после проверки отсутствия ссылок из pod. Наличие старого ConfigMap само по себе не разрешает откат bootstrap, ключей или протокола. При configuration.retain=false сохранение отключено.

Helm не дает атомарной транзакции над несколькими объектами. Проверочный lifecycle работает в выделенном namespace без параллельных административных изменений: manifest проверяется заранее, отсутствие новых имен фиксируется до Helm, UID созданных объектов — после чтения результата с проверкой release ownership. Внешние SA, Lease, state и target Secret не входят в release.

helm lint operator/charts/sekvyr-operator -f /secure/operator-values.yaml
helm template operator operator/charts/sekvyr-operator --namespace apps \
  --include-crds -f /secure/operator-values.yaml
# Установку в кластер выполняют только после проверки итогового manifest.
helm upgrade --install operator operator/charts/sekvyr-operator --namespace apps \
  -f /secure/operator-values.yaml

Права и монтирование

Runtime Role действует только в namespace установки: чтение SekvyrStore/SekvyrSecret, обновление status, GET трех bootstrap Secret и закрепленных CA ConfigMap, работа с одним заранее созданным Lease. При sync.enabled=true добавляются Update строго state Secret и имен из installation.allowedTargetSecrets, GET этих целей и namespace-scoped Create Secret. RBAC Kubernetes не умеет ограничивать Create по resourceNames, поэтому этот режим допускается только в доверенном административном namespace с обязательной runtime-проверкой allowlist, защищенных целей и ownership. Chart отвергает bootstrap names и защищенные префиксы в target allowlist.

При отдельном rollout.enabled=true обязательны включенная синхронизация и непустой административный список rollout.allowedDeployments. Только в этом режиме добавляются GET и PATCH Deployment с точными resourceNames в namespace установки. Список и флаг попадают в installation JSON, отдельный runtime flag также должен разрешать rollout. Запрос CR и разрешения binding должны соответствовать административному списку.

У оператора нет list/watch/patch/delete Secret, Deployment update/list/watch/scale, удаления pod, TokenRequest API или impersonation. При выключенном rollout прав на Deployment нет. Delete policy реализуется точным ownerReference и Kubernetes GC, без runtime Secret delete. Определение CRD устанавливает администратор кластера. Дополнительные права отдельного fencer появляются только при HA opt-in и описаны ниже.

Identity, trust и конфигурация смонтированы только для чтения. State проверяется отдельным GET без кеширования Secret. Для Kubernetes API и панели спроецированы разные короткоживущие ServiceAccount tokens: для панели audience строго sekvyr. Автоматическое монтирование токена отключено. Метрики выключены, процесс непривилегированный, root filesystem только для чтения.

auth.tokenExpirationSeconds задает запрошенный TTL projected tokens панели и fencer: от 600 до 3600 секунд, по умолчанию 3600. Audience остаются фиксированными sekvyr и sekvyr-fence. Проекция Kubernetes API сохраняет собственный TTL 3600. Фактическое обновление файла проверяется отдельно на живом kubelet в том же Pod; изменение YAML или новый Pod этого не доказывают. Обновление токена также не означает ротацию JWKS signer.

CA панели задается в Store, CA witness - необязательным installation.witnessCAConfigMapRef. Обе ссылки должны соответствовать административным pins в installation.caConfigMaps. Runtime получает сертификаты отдельным GET и проверяет UID и DER-set hash перед HTTP, без произвольных путей или отключения TLS-проверок. Без custom CA используются системные корни.

Проверка ресурсов

CRD содержат структурную схему и CEL для неизменяемых ссылок, режима шифрования, целевого имени/типа/deletionPolicy, согласованности selection/rollout и уникальности binding names/resource names/targets внутри Store. Межресурсная авторизация, UID, защищенные цели, NFC/Unicode, CA pins и конфликты между Store проверяются контроллером отдельно.

Для отклонения неизвестных полей используйте fieldValidation=Strict. Обычные клиенты Kubernetes могут предупредить об неизвестных полях или удалить их: схема не сохраняет и не использует такие поля. Правила структурных схем и CEL Kubernetes.

Helm не обновляет существующие CRD из каталога crds/ автоматически при upgrade. Изменения CRD проверяются отдельно администратором; их удаление с пользовательскими ресурсами не входит в обычное удаление workload.

Экспериментальный HA fencing

Readiness fencer использует HTTPS /readyz с проверкой актуального journal/enrollment без кеша. ha.fencer.readinessTimeoutSeconds задает целое число от 1 до 30 секунд, по умолчанию 10; periodSeconds=10, failureThreshold=3 и successThreshold=1. Неуспешная проверка журнала сохраняет отказ readiness. Liveness отдельно проверяет процесс через HTTPS /healthz с прежним timeoutSeconds=1 и теми же period/threshold. Увеличение readiness timeout не доказывает доступность хранилища и не меняет правила admission. Значение 1 позволяет явно воспроизвести прежний таймаут при проверке совместимости.

Для согласованного восстановления bootstrap режим ha.maintenance=true требует ровно replicas=0 у оператора и сохраняет не менее двух replicas fencer. Обычный HA требует не менее двух replicas оператора; вне HA maintenance запрещен. После подписанного восстановления оператор возвращается через явный Helm upgrade с ha.maintenance=false и replicas=2. Это административная остановка, а не автоматическое восстановление.

ha.webhook.retiredStateSecrets по умолчанию пуст. Администратор может передать точные name/creation UID прежних state Secret этой же установки. Старые имена сохраняются вместе с текущими в admission scope и protected targets; права Role и активный набор fencer не расширяются. Обнаружение UID из живого объекта, принятие объекта с новым UID и автоматическая очистка старых pins не выполняются.

ha.enabled=true требует ha.trial=true, включенной синхронизации и не менее двух replicas оператора. Допускается только одна journal log/view на установку. До установки администратор создает все state/target Secret и разрешенные Deployment, ServiceAccount, Lease, независимую journal registration и enrollment. В values закрепляются их UID. Runtime HA не получает Secret create и не принимает объект с новым UID под старым именем.

ha.config переносится в installation.ha: закрепленные fencer/gateway origins, CA references, ссылка на отдельный read-only mTLS client Secret оператора и journal registration. CA references должны входить в административные CA pins. ha.managedObjects содержит полный набор state, target Secret и разрешенных Deployment с apiVersion, kind, namespace, name и UID. ha.namespaceUID, ha.operatorServiceAccountUID и ha.leaseUID должны совпадать с независимым enrollment.

Отдельный fencer ServiceAccount находится в namespace установки. Оператор не получает его signing key, TLS private key или отдельный gateway write credential. Эти три неизменяемых Opaque Secret задаются ссылками и UID в ha.fencer. Их существование и содержимое закрепленных ключей проверяются отдельным GET при запуске fencer. Values не содержат приватные материалы. Публичный ha.webhook.caBundle допустим в Helm; приватный TLS key хранится только в существующем Secret. Пример tests/chart/values.ha.public.example.yaml предназначен только для структурной проверки.

Fencer выполняет TokenReview projected token с audience sekvyr-fence, проверяет bound Pod UID, ServiceAccount и фиксированную полную Lease holder identity процесса. Каждая попытка journal CAS повторяет прямой Lease GET. Подписанный grant закрепляет canonical snapshot, term и весь набор object UID. Fencer ставит fence-only барьер на каждом объекте через UID/resourceVersion CAS, затем пишет независимую подписанную activation. Только активная сессия разрешает обычные записи. Изменение canonical snapshot инвалидирует старую сессию, даже если plaintext не изменился.

Включается новый ValidatingWebhookConfiguration с failurePolicy=Fail, sideEffects=None и точными matchConditions для namespace и managed names. Обычная запись требует текущий онлайн grant, тот же fence и fixed write-session hash. Admission не читает Lease и не делает Kubernetes GET других объектов. Явные ha.fencer.bootstrapSubjects предназначены только для согласованных bootstrap/recovery субъектов с точным username и UID. При недоступном webhook обычный доступ к защищенным объектам блокируется, поэтому административное восстановление и удаление webhook планируются заранее.

Fencer получает namespace-scoped GET Pod без list/watch для проверки динамических имен; GET только закрепленных ServiceAccount, Lease и трех material Secret; GET/PATCH только managed Secret и Deployment. Отдельный ClusterRole разрешает только TokenReview create и GET точного namespace. Оператор этих кластерных прав не получает. Шаблон webhook обычно использует Service <release>-fencer, порт 9443, путь /admit; ha.webhook.serviceName позволяет направить только этот trial webhook через изолированный тестовый relay.

Границы этапа

Initial Secret create и включение rollout не создают исторического перезапуска. Фактическое изменение данных существующего Secret может создать pending intent, независимо закрепленный в защищенном state. После актуальной E2E2 witness-проверки и повторной авторизации оператор меняет только свою аннотацию pod template с непрозрачной ревизией, используя Deployment UID/resourceVersion CAS. Pod должен действительно использовать целевой Secret. Paused/progress deadline, замена UID и потеря state блокируют действие; отказ witness не разрешает выполнять старый pending intent. DataCurrent и RolloutReady показывают разные состояния.

Development filesystem witness на локальном стенде не доказывает WORM или независимость производственного хранилища. Эти гарантии требуют последующих этапов и отдельного аудита. При выключенной синхронизации Ready/DataCurrent остаются ложными.

Trial HA предполагает честный Kubernetes API server с монотонными resourceVersion и storage CAS. Уже одобренная задержанная запись старого владельца должна конфликтовать после установки нового барьера. Восстановление etcd с откатом resourceVersion при сохранении старого запроса, компрометация текущего ServiceAccount или администратора, Byzantine storage и отказ всего единственного узла этими проверками не покрываются. Ни число replicas, ни локальная имитация ledger не доказывают production HA или WORM.
