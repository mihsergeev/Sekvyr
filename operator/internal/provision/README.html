sekvyr-provision: только офлайн-подготовка

Версия инструмента 0.1.0-rc.1. Команды не вызывают HTTP, Kubernetes, Helm или storage commit, не обнаруживают ключи и не создают fence grant, activation или head proof. Выходы являются подготовленными файлами, а не доказательством публикации, актуальности, WORM retention или состояния Kubernetes.

sekvyr-provision version
sekvyr-provision <keygen|public|genesis|snapshot|transition|bootstrap|recovery> \
  --work-dir /private/provision --input request.json --output new-artifacts

Файловый интерфейс поддерживает Linux и закрыто отказывает на других платформах. Существующий work-dir и вложенные каталоги принадлежат текущему UID и имеют private permissions (обычно 0700), входные файлы - private regular files (обычно 0600). Все ссылки на файлы относительны work-dir. Symlink в пути, hardlink входного файла, FIFO, parent traversal и перезапись запрещены; обработка основана на dirfd/O_NOFOLLOW. Выходной каталог создается исключительно заново, файлы - 0600. При частичной ошибке записи каталог сохраняется для ручной проверки, повторный вызов его не принимает. Это не защита от привилегированного администратора хоста или произвольных действий другого процесса того же UID.

Ключи и plaintext передаются только через эти защищенные файлы. Аргументы CLI не содержат секреты; stdin и переменные окружения для секретов не используются. stdout содержит только счетчик артефактов, имя операции и явные offline/online-verification flags; ошибки закрыты константным сообщением. Входной JSON ограничен 64 MiB, дубликаты, неизвестные поля, неверный регистр, null scalar, дроби, некорректный Unicode и неоднозначные формы отвергаются существующим строгим codec.

Команды и формы входа

Полные типы запросов находятся в types.go. Каждое поле запроса обязательно, включая pending и пустой state_file для initialize. Вложенные протокольные структуры используют существующую схему; ее nullable union fields сохраняются. Примеры ниже содержат только названия файлов.

КомандаЗапрос и результат
keygen{"role":"publisher"}. Ровно одна роль: admin, publisher, witness, fencer, node или read. Ed25519 роли и P256 node: private.pem (PKCS8), public.json (роль, fingerprint, canonical unpadded base64url public key). Read: только read-key.bin, 32 случайных байта, без публичного hash/oracle и без bundle других private keys.
public{"role":"node","private_file":"node/private.pem"}. Создает только public.json; read role не имеет public operation. Указание role само по себе не дает полномочий: роль ключа в authority проверяется signed chain и ее историческим разделением ролей.
genesisbody_file, admin_key_file, admin_public_file. Явный независимый admin descriptor должен совпасть с private key и GenesisBody.AdminKey. SignGenesis → NewGenesisRecord → Replay до записи. Выход: record.json, records.json, registration.json с original-admin/genesis/floor pins. Это еще не online initialization.
snapshotchain, pending, header_file, plaintext_file, read_key_file, publisher_key_file, publisher_public_file, recipient_public_file. Scope/next snapshot sequence/previous hash привязаны к replay. Private publisher должен совпасть с явно проверенным descriptor. SealSnapshot → VerifyEnvelope → Decrypt и точное сравнение full plaintext; WrapReader → строгая shape/context/signature проверка. Выход: envelope.json, reader-wrap.json, candidate.json. Для обычных current epochs/pub дополнительно record.json после полного candidate Replay.
transitionchain, body_file, admin_key_file. Body - точный TransitionBody, без автоизменения cursor/revision/epochs. Поддерживает существующие enrollment, rotation и recovery kinds. SignTransition → full candidate Replay с original registration. Проверяются admin handover, прошлые role assignments, epochs и обязательный activating envelope. Выход: transition.json и record.json.
bootstrapchain, config_file, receipts_file, binding_file, node_public_file, trust_key, publisher_key_id. Receipts: Enrollment и recovery.Binding от независимого администратора с точными UID/generation. Config.Validate, существующие pure Store/CR validators, BindingIdentity, scope/receipt/target/namespace checks; publisher выбран явно из replayed authority. Только здесь допустимо явное Identity="": после проверки binding вычисляется его существующий Go JSON hash. Непустая неправильная Identity отвергается. DecodeTrustBundle и Authorize перед записью. Выход: installation.json, trust.json, state-marker.json и receipts.json с нормализованной Identity и неизменными UID/generations. stdout сообщает лишь безопасный identity_computed flag. Это unsigned материалы: Kubernetes references/pins и online enrollment должны быть проверены отдельно.
recoverychain, config_file, receipts_file, binding_file, body_file, state_file, admin_key_file. Body - точный recovery.Body с новым recovery ID, cursor, snapshot, UID/generations и expiry. Для initialize state_file пуст; для recover явный retained-state file обязателен, в том числе если он пустой. StateDigest сравнивается по точным байтам без JSON normalization. Нормализованные reviewed receipts и body обязаны иметь непустую совпадающую Binding.Identity: recovery ее не вычисляет и не подставляет. Binding.Identity использует существующий Go JSON hash, а не JCS. Sign → recovery.Verify; срок не больше 24 часов относительно вызова. Выход: plan.json для отдельного native checkpoint-recovery.

Отдельные authority pins и replay

"chain": {
  "registration_file": "reviewed-registration.json",
  "records_file": "saved-complete-signed-records.json",
  "expected_cursor": {"journal_sequence":"...","record_hash":"..."}
}

RegistrationFile - независимо доставленные original admin public key, genesis hash и минимальный cursor. RecordsFile - ограниченный полный подписанный массив от genesis; JSON CurrentState от панели не принимается. Применяются лимиты существующего journal, проверка каждого record и signatures, отдельная проверка floor hash на нужной позиции и точное сравнение final expected cursor. Online receipts не фабрикуются: offline Replay не проверяет свежесть, полноту относительно живого хранилища, версии объектов или COMPLIANCE retention. Валидный старый prefix может быть ниже реально существующего head; его обязан отвергнуть последующий online CAS/floor gate. Нельзя молча пересчитывать candidate после CAS conflict или lost acknowledgment: сначала разрешается точный ранее сохраненный результат.

Pending rotation

Activating snapshot нужно зашифровать до подписи административного transition. При новых read/publisher epochs, publisher key или restore обязательно pending:true. Проверяются scope, next sequence, previous hash, независимый publisher descriptor, допустимый следующий epoch и существующий restore history. Выход не содержит canonical record, commit receipt или новую authority. candidate.json явно указывает pending=true, committed=false. Pending нельзя выдать за current. Затем transition включает именно этот envelope и новый authority; полный signed Replay обязателен до выхода transition, а online CAS и runtime trust gates сохраняются. Менять epoch без нового случайного AES key недостаточно для отзыва старого node: администратор должен отдельно создать свежий read key и нужные wraps.

Проверки и границы

Тесты используют только новые случайные тестовые ключи и локальные временные файлы. Они потребляют выходы существующими VerifyEnvelope/UnwrapReader/Decrypt, Replay, installation.Decode, DecodeTrustBundle и recovery.Verify. Негативы включают плохие pins/floors/cursors, несовпадающие epochs/pub, pending-as-canonical, отсутствующий activating envelope, чужой recipient, role-confused genesis, UID mismatch, expiry, измененные retained state bytes, symlink/hardlink/FIFO и overwrite. Реальный install, native recovery с кластером, online storage CAS и E2E выполняются отдельно интегратором; успешный unit test не подменяет их.
