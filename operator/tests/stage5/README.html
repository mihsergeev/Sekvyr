Живой E2E этапа 5

Отдельный изолированный прогон проверяет настоящий Deployment приложения с envFrom Secret. Приложение читает окружение один раз при запуске, не отслеживает файлы и не перезагружает настройки самостоятельно. Новое значение возможно только в новом процессе pod.

Это описание тестового harness и критериев приемки. Само наличие исходников не означает успешного живого прогона: его отдельный результат появляется в $TASK_DIR/results.json только после всех проверок.

На общем стенде может работать другой контроллер автоматических перезапусков. Тестовый Deployment явно задает reloader.stakater.com/auto: "false" и оба typed auto-флага false, чтобы измерять только действие этого оператора. Глобальная конфигурация и существующие workloads не меняются. Без этого opt-out Reloader может добавить переменную окружения и отдельный ReplicaSet, что делает такой прогон непригодным для доказательства единственного rollout. Официальные правила аннотаций Reloader.

Административные границы

Helm / installationsync.enabled=true, отдельный rollout.enabled=true и непустой точный список rollout.allowedDeployments. По умолчанию оба действия выключены.

Подготовка

Панель, PostgreSQL, отдельный TLS witness и независимо закрепленный bootstrap берутся из общих helpers этапа 4. Новый каталог /opt/sekvyr-trial/sekvyr-stage5-YYYYMMDD-xxxxxxxx получает четыре новых namespace с тем же префиксом. Ключи и учетные данные создаются только в private, вне репозитория и Helm values. Одноразовый vault root key сохраняется с правами 0600; после планового перезапуска панель явно открывается по owner API через TLS.

Перед bootstrap harness проверяет отсутствие обеих Sekvyr CRD. Их UID и UID namespace сохраняются из ответов создания. Образы передаются по digest и должны быть заранее собраны и импортированы в разрешенный тестовый containerd. Адрес сервера, имя ноды и реальные административные пути не записываются в эти исходники.

python3 operator/tests/stage5/run.py --task-dir "$TASK_DIR" \
  --chart-path "$REVIEWED_CHART" --node-name "$APPROVED_NODE_LABEL" \
  --expected-kubernetes "$EXPECTED_VERSION" --storage-class "$APPROVED_STORAGE_CLASS" \
  --phase infrastructure --panel-image "$PANEL_IMAGE_BY_DIGEST" \
  --witness-image "$WITNESS_IMAGE_BY_DIGEST" --database-image "$POSTGRES_IMAGE_BY_DIGEST" \
  --python-image "$PYTHON_IMAGE_BY_DIGEST"
# Те же общие параметры: затем --phase bootstrap
# Только после готовности интеграции: --phase exercise --operator-image "$OPERATOR_IMAGE_BY_DIGEST"

Проверки живого прогона

  • Initial Secret create и последующее включение rollout не создают исторического запроса на перезапуск.
  • Одно фактическое изменение данных создает ровно один новый ReplicaSet UID, меняет только свою UID-аннотацию template и дает новый pod/boot ID с новым окружением. Число Deployment generation сохраняется только как диагностика: Kubernetes может повышать его также при изменении metadata annotations.
  • Повтор reconciliation и новый ciphertext с прежним plaintext не меняют pod template или pod UID.
  • Fork, подмена подписи/ciphertext, replay и отказы панели/witness сохраняют Secret и template. Восстановление без новых данных не запускает исторический перезапуск.
  • Для детерминированной проверки pending Deployment временно paused. Затем witness недоступен, Deployment unpaused, оператор перезапускается: intent остается замороженным. Возврат witness и новый строгий current sync завершают intent ровно один раз.
  • Отказ административного allowlist, suspend/resume, новое имя-совпадающее Deployment UID и потеря/замена state не обходят проверки.
  • RBAC проверяется реальным can-i, статусы и логи проверяются на тестовые credentials, read/node keys и plaintext canary.

Fault injection через административный exec в собственную тестовую панель и ручное удаление тестового Deployment принадлежат только этому изолированному прогону. При проверке UID recreation новый pod может появиться из-за действия администратора; harness отдельно проверяет, что оператор не меняет template нового Deployment по старому intent.

Результат и уборка

JSON содержит только список проверок, версии/digest и безопасные доказательства смены pod/boot ID и поколения template. Значения DEMO_VALUE, read key, node private key и токены не экспортируются. Приложение возвращает только generation, boot ID, PID и SHA-256 тестового значения.

Общий operator/tests/stage4/cleanup_cluster.py работает по UID, записанным при создании, проверяет точную CRD schema и отсутствие чужих CR. Удаление требует явного --execute и server-side DeleteOptions.preconditions.uid. Сначала удаляются четыре namespace этого прогона, затем две закрепленные CRD. Перед уборкой отдельно фиксируют готовность ноды и фоновых нагрузок, после нее закрывают только scoped port-forward процесса.

Development filesystem journal не доказывает WORM или независимость производственного restore. Здесь не выполняются production rollout, выпуск, ротации или изменения существующих приложений.
