Живой E2E этапа 4

Изолированный локальный kind sekvyr-stage4, Kubernetes 1.37.0. В нем запускаются настоящие панель и PostgreSQL, отдельный TLS witness с development filesystem journal, оператор и Python pod с смонтированным Secret. Production и существующие данные не используются.

Поддерживается также driver k0s на заранее разрешенном тестовом сервере. Весь harness запускается на сервере из закрытого каталога /opt/sekvyr-trial/sekvyr-stage4-YYYYMMDD-xxxxxxxx; namespaces получают тот же уникальный префикс. Транспорт выполняет только sudo -n k0s kubectl и не меняет cluster configuration. Перед установкой он отказывается заменять существующие Sekvyr CRD. Адрес сервера и настоящее имя ноды передаются отдельно и не сохраняются в исходниках.

Панель и witness имеют разные сгенерированные корни TLS. Все ключи, пароли, service bearer и доверенные пакеты создаются во временном каталоге с закрытыми правами вне репозитория. Helm получает только ссылки, UID и разрешенные origins. Оператор входит по настоящему projected ServiceAccount JWT с audience sekvyr; панель проверяет его ключами JWKS кластера.

Одноразовый root key из ответа vault init сохраняется только в private с правами 0600. После запланированного перезапуска панели harness явно открывает vault через owner API по TLS. Штатный sealed gate остается включенным; его отказ не обходится настройками оператора или продукта.

Последовательность

  1. prepare.sh проверяет pinned kind binary/node image и создает только названный тестовый кластер. Повторное использование требует явного --reuse. Он выводит TASK_DIR с kubeconfig.
  2. Соберите свежие образы из текущих исходников: панель из корня через backend/Dockerfile, witness из operator/ через cmd/witness/Dockerfile, оператор из operator/. Образы и зависимости передаются тесту только по digest; локальная загрузка в kind не публикует их в registry.
  3. Фаза infrastructure загружает образы, создает ключи, namespaces и PVC, запускает PostgreSQL/панель, отдельно выполняет signed genesis Job и запускает witness без повторной инициализации журнала.
  4. Фаза bootstrap использует реальные owner API, регистрирует JWKS, машинную личность и полный view grant, публикует первую ревизию и создает независимо закрепленный bootstrap оператора.
  5. Фаза exercise устанавливает Helm с явным sync opt-in и проверяет Secret, живое приложение, отказы и восстановление. Последняя проверка намеренно оставляет оператор с замененным state и ложным Ready; это ожидаемый fail-closed результат, а не рабочая установка.
bash operator/tests/stage4/prepare.sh
# TASK_DIR берется только из вывода prepare.sh.
python3 operator/tests/stage4/run.py --task-dir "$TASK_DIR" --phase infrastructure \
  --panel-image "$PANEL_IMAGE_BY_DIGEST" --witness-image "$WITNESS_IMAGE_BY_DIGEST" \
  --database-image "$POSTGRES_IMAGE_BY_DIGEST" --python-image "$PYTHON_IMAGE_BY_DIGEST"
python3 operator/tests/stage4/run.py --task-dir "$TASK_DIR" --phase bootstrap
python3 operator/tests/stage4/run.py --task-dir "$TASK_DIR" --phase exercise \
  --operator-image "$OPERATOR_IMAGE_BY_DIGEST"

Для k0s каталог и source upload подготавливает администратор, затем к каждой фазе добавляются --driver k0s --expected-kubernetes "$EXPECTED_VERSION" --node-name "$APPROVED_NODE_LABEL". Образы собираются и импортируются отдельным проверенным процессом; harness не ставит Docker и не чистит общий containerd. При отсутствии Helm его приватный путь задается переменной HELM_BIN. Локальный cleanup.sh относится только к kind; серверную уборку выполняют отдельно по точному префиксу созданных namespaces и каталогу задачи.

Критерии

  • Существующий чужой Secret не принимается под управление и не меняется.
  • Полный подписанный view проходит панель, независимый witness и оператор, после чего приложение читает две canary keys из смонтированного Secret.
  • Новая ревизия меняет значения и перезагружает конфигурацию приложения при прежних boot ID и PID. Приложение разрешает AtomicWriter ..data один раз на чтение пары файлов.
  • Свежий ciphertext с прежним plaintext двигает accepted checkpoint, сохраняя data revision и состояние приложения.
  • Реальный witness CAS отвергает competing fork. Поврежденная подпись, ciphertext и старый signed blob на адресе нового hash не приводят к применению.
  • Старый panel index не заменяет свежий nonce-bound canonical head. Остановка панели или witness сохраняет target, дает ложный DataCurrent и восстанавливается после возврата сервиса.
  • Перезапуск оператора сохраняет node identity и checkpoint. Отсутствующий или замененный state не восстанавливается автоматически.
  • Runtime не имеет Secret list/watch/patch/delete и права менять Deployment. Логи и CR status не содержат credentials, read keys или demo plaintext.

Fault injection выполняется только через административный exec в тестовую панель и ее собственную PostgreSQL-таблицу staged ciphertext/index. Это намеренный обход owner validation для имитации скомпрометированного source storage, а не дополнительный product API. Не используйте такие приемы на рабочей панели.

Границы результата и уборка

Development filesystem journal доказывает только проверяемые CAS, replay, persistence и fail-closed свойства этого локального стенда. Обычный PVC не доказывает WORM или независимость производственного хранилища от общего restore. Production storage gate, ротации и аудит относятся к следующим этапам. Существующий Kubernetes Secret и память приложения могут сохранять старые значения при недоступном источнике; Ready/DataCurrent сообщают об этом отдельно.

Машинный итог сохраняется в $TASK_DIR/results.json без значений секретов. Закрытый подкаталог private содержит только временные тестовые учетные данные и не переносится в отчет или репозиторий. После просмотра результата:

bash operator/tests/stage4/cleanup.sh "$TASK_DIR"

Уборка проверяет точный префикс и resolved path, удаляет только этот кластер, его сгенерированные приватные материалы и kubeconfig. Другие Docker-контейнеры, кеши, образы и временные каталоги не затрагиваются.

Для серверного k0s используется отдельный cleanup_cluster.py. UID четырех namespace и двух CRD сохраняются из ответов создания в private bootstrap metadata. Проверяются Store UID, эти UID, точная схема и отсутствие CR вне namespace прогона. Каждое удаление передает серверу DeleteOptions.preconditions.uid; отсутствие creation-time pins блокирует уборку. Удаление требует явного --execute и согласования завершения всех тестов с PostgreSQL. Сначала удаляются четыре namespace вместе с оператором, затем повторно проверяются и удаляются закрепленные тестовые CRD. Образы, исходники и приватный каталог скрипт не удаляет.
