Этап 7: приложение, Helm и проверяемые границы

Это исходники испытаний, а не отчет об успешном живом прогоне. Фактический результат, версии API, образы и завершенный cleanup фиксирует координатор после выполнения. Рендер для Kubernetes 1.34.1 и 1.37.0 не доказывает совместимость runtime. Подготовка и изменения инфраструктуры выполняются только отдельным Cluster provider в выделенных namespace.

Для Secret volume каталог ..data разрешается один раз на чтение набора ключей: смена проекции между чтениями не должна смешивать поколения. Настоящий lifecycle Helm

lifecycle = HelmLifecycle(cluster, helm_binary, chart_path,
    release_name, apps_namespace, external_pins)
lifecycle.install(reviewed_values)
lifecycle.upgrade(reviewed_next_values)
lifecycle.uninstall()

Каждая команда получает точный kubeconfig и namespace. До install проверяются отсутствие release и всех новых имен. Cluster сохраняет preflight с namespace UID, hash manifest и списком отсутствующих объектов до запуска Helm. После Helm читает созданные объекты, сверяет release metadata и manifest с server defaults, сохраняет UID с честным provenance post-create-read. При ошибке Helm сохраняются найденные частичные ресурсы; автоматического повторного install или принятия существующих объектов нет.

Внешние SA/Lease используют create=false и заранее известные UID. Они не появляются в render и не получают метаданные release. Перед upgrade/uninstall проверяются UID собственных объектов и неизменность внешних. При upgrade разрешено убирать из manifest только сохраняемые immutable ConfigMap; новые hash revisions проходят отдельный preflight. Повторное принятие старой сохраненной ревизии запрещено. Uninstall проверяет исчезновение managed workload/RBAC и сохранение всех известных конфигурационных ревизий и внешних UID. Окончательный cleanup этих ConfigMap выполняет Cluster по pins после проверки отсутствия ссылок.

Cluster-scoped HA объекты требуют отдельного manifest approval до первого создания. Изменять существующие webhook или ClusterRole через этот helper нельзя: для этого нужен отдельный guarded review. Helm lifecycle не ставит и не удаляет CRD (--skip-crds); проверка административного обновления схемы проводится отдельно с сохранением существующих CR. Native Helm не является транзакцией с UID/RV CAS на каждом запросе: испытание требует эксклюзивного административного владения fixture. После ошибки или потери контекста требуется явный разбор сохраненных receipts, автоматического восстановления с новым контекстом нет.

Панель, проекции JWT и изоляция

PlainInstallation(coordinator, provider, image, helm, chart) использует отдельный namespace isolation. prepare() создает SA/Lease и bootstrap с creation UID pins, затем готовит Plain source через PanelCases. prepare_store(target, selection, rollout_deployments) проверяет структуру CRD до CREATE и возвращает values. Приложения с нулем реплик создаются отдельно до передачи rollout allowlist. Только явный install() запускает настоящий Helm. current(after_success) требует актуальные поколения CR и Store и успешную попытку чтения, а target_ref(generation, demo_value, after_success) сопоставляет Plain record защищенного state с реальным target UID и статусной ревизией; он не принимает цель под управление cleanup и не меняет ее.

Machine policy панели сопоставляет namespace и имя SA. Harness отдельно закрепляет creation UID SA, а runtime проверяет административный pin прямым GET. Эти проверки не означают, что backend регистрирует SA UID или немедленно отзывает offline JWKS token после удаления Pod. Для Plain DataCurrent означает успешное авторизованное чтение панели, без signed witness или независимой canonical freshness.

Plain fixture использует отдельные project/environment/machine, pinned identity и immutable trust schemaVersion=1 с protocol=plain-v1. State содержит bindings с mode=Plain и head=null; witness checkpoint для Plain неприменим. E2E2 использует независимый существующий provider. Путь selection в обоих случаях согласуется с /runtime. Target UID для проверки приложения передается только после fresh DataCurrent и сопоставления protected state с реальным Secret.

В projected tokens запрашивается TTL 600 секунд. Проверка ротации ждет фактической замены token-файла kubelet в том же Pod, сопоставляет bound Pod UID и успешную авторизацию обоих токенов. Это отличается от смены JWKS signer KID. Принудительная смена clock, запись токена руками и новая pod не заменяют такой тест. Смена signer допускается только в выделенном control plane по отдельной процедуре координатора.

Роли namespace: apps, isolation, panel, witness, gateway, storage. Helpers не выбирают реальные имена и адреса. Namespace и все изменяемые ресурсы закреплены по creation UID, JSONPatch содержит UID/resourceVersion tests. Приложение не получает AWS credentials, ключи journal или приватные key из другой роли. Наличие policy manifest без фактической CNI enforcement не считается доказательством сетевой изоляции.

Secondary case использует уже разрешенные Plain project/path и ту же установку. Helm расширяет только allowedTargetSecrets на одно новое имя; остальные gates и pins сохраняются. Новый Store, binding и CR получают отдельные creation UID. Отказ засчитывается только как DataCurrent=False / PanelUnavailable при BootstrapReady=True текущего поколения и отсутствии какого-либо успешного получения. Неправильный ключ, невалидный state или пустой source не заменяют проверку sealed panel до первой цели. После unseal новый UID сопоставляется с новой записью защищенного state; прежние binding, данные, revision и процессы приложения остаются прежними.

Sealed 503 и transport outage доказываются отдельно. Пока vault еще sealed и новой цели нет, координатор останавливает только свой закрепленный Deployment панели. Требуются наблюдаемое поколение scale=0, отсутствие Pod и готовых Service endpoints, затем новая попытка CR после этой проверки. Внутренний finally возвращает тот же UID в scale=1/Ready, переподключает приватный forward, выполняет login и подтверждает initialized + sealed. Только после этого внешний контекст делает явный unseal. Неудачное восстановление, чужой UID, старый timestamp или только запрос scale без фактической остановки не дают успешного доказательства.

Ротация API-server signer допускается только у creator-pinned kind и после остальных операторных сценариев. Если им еще нужно работать во время ротации, администратор отдельно согласует overlap JWKS для каждого собственного зарегистрированного потребителя; чужие registrations не меняются. Иначе новый projected token может временно не приниматься потребителем со старым offline JWKS. Возвращается старый signer с временным overlap verifier до удаления всего своего kind; точное восстановление исходного manifest не заявляется. Немедленный отзыв уже выданной machine session не проверяется этим сценарием.

При использовании kubectl port-forward к панели рестарт API server может оставить старый forward непригодным. Координатор передает необязательный callback after_control_plane_ready(phase) для переподключения только своего panel forward по уже рассмотренным UID/scope guards. Закрытые фазы: rotated после Ready, независимой проверки overlap и нового подписанного bound token, непосредственно перед проверкой retirement; restored после восстановления signer и проверки verifier, перед owner update JWKS. Callback не меняет issuer/JWKS trust, не обходит TTL, не делает автоматический retry или новую авторизацию. Его исключение распространяется; finally сохраняет восстановление исходного signer. Без callback прежний порядок сохраняется. Этот источник исправляет будущую воспроизводимость: фактическая прерванная попытка с устаревшим forward остается отдельной историей ручного продолжения, а не доказательством живого выполнения callback.

Случай прерванного наблюдения во время удаления прежнего Pod продолжают с тем же сохраненным before и уже опубликованным поколением. Повторная публикация, новый intent или новый baseline не заменяют доказательство единственного ожидаемого rollout. Ошибки чужого owner/namespace остаются жесткими отказами. Созданные вторичные Store и CR с недоказанной outage phase не переигрываются автоматически после ошибки: нужен разбор сохраненных receipts.

Локальные guards проверяют ограничения scope, UID, порядок preflight/capture, запрещенный adoption, retention, credential isolation и чтение canary. Они не заменяют живые проверки rollout, kubelet projection, реального агента, отказов, смены лидера, API admission, Helm upgrade/uninstall или другого minor Kubernetes. Результаты этих сценариев до выполнения остаются pending. Выпуск и этап 8 не выполняются.

Отдельный kind на удаленном Linux-host

Это профиль приемки этапа 7, не выпуск и не production deployment. Он не использует Windows receipt и не расширяет WSL cleanup. Координатор заранее фиксирует независимый baseline существующих Docker-ресурсов. RootTask должен иметь собственную квитанцию CREATE receipts/root-task-create.json; rootTask и новый runtime принадлежат UID/GID 0 с mode 0700. Root SSH не нужен: подготовленные команды запускаются через разрешенный sudo -n. Python должен поддерживать setns и pidfd, host должен быть Linux amd64.

Три приватных инструмента проверяются по независимо рассмотренным SHA-256 и версиям: kind 0.33.0, Helm 4.3.1, kubectl 1.37.0. Официальный digest-pinned node image должен уже разрешаться по точному имени и RepoDigest. Создатель не выполняет pull, tag, Docker load, настройку daemon, sysctl, часов или существующих workloads. Неудачная предварительная проверка не дает разрешения принимать найденный по имени контейнер.

Отсутствие прямых команд sysctl/firewall в creator не гарантирует отсутствия побочных изменений Docker на общем хосте. До создания первой сети независимый preflight должен сохранить IPv4/IPv6 forwarding (all/default/per-interface), RA и bridge sysctl, IPv6 address flags/anycast, firewall/routes и полный image inventory, включая скрытые images. В выполненном trial исходные sysctl не были сняты: после cleanup сохранены дополнительные пустые IPv6 объекты и локальный kernel anycast; точный исходный global state не восстановим по одному маршруту. Пользователь отдельно выбрал сохранить текущие глобальные настройки. Это известное ограничение приемки, не доказательство отсутствия изменений хоста. Автоматический откат неизвестных sysctl, счетчиков и маршрутов запрещен.

Перед kind create сохраняются отсутствие имени, полные хеши чужих Config/Env/HostConfig/Args/Networks и состояния запуска. Только порядок Mounts нормализуется; все поля сохраняются. CREATE-происхождение CID и независимая квитанция rootTask/private/creator/creation.json сохраняются до caps и CRD. Runtime marker private/remote-kind-capability.json связывает эти записи с boot/daemon, точными image/CID/labels, PID/starttime, ресурсами 4 CPU / 8 GiB RAM / 8 GiB memory+swap, volume и network ID. Все обращения exec и root-child setns повторно проверяют этот capability. Служебный recovery CLI ограничен рассмотренными digest d328 и SHA-256 641c; прежний профиль 960d остается прежним.

Cleanup сохраняет строгий network hash со всеми полями Docker inspect, кроме Containers. В Docker 29 после отключения последнего своего endpoint меняются счетчики IPsInUse и DynamicIPsAvailable в Status.IPAM.Subnets; hash gate может остановиться уже после удаления своего CID и volume. Повторять cleanup в таком состоянии нельзя. Отдельное удаление exact network ID допустимо только после рассмотрения creation receipt, отсутствия сети в preflight, пустых attachments и неизменности host/daemon, а также точного воспроизведения исходного hash заменой только доказанных счетчиков в памяти. Все остальные поля должны совпасть, чужой baseline должен сохраниться. При любом другом изменении сеть сохраняют для разбора; исключение Status целиком, удаление по имени и global prune запрещены. Этот порядок описывает отдельное контролируемое продолжение, а не автоматический retry.

Сетевые пути до первой публикации Plain

После подготовки инфраструктуры, witness и панели создается Plain установка с приложениями в scale=0. Hook вызывается строго после настоящего Helm install и capture UID, до owner publish и запуска этих приложений. Его ошибка оставляет созданные ресурсы для разбора и не запускает publish. # cleanup(owner, execute=True)

Cleanup адресует точный CID и отдельно закрепленные anonymous volumes. Сеть удаляется только если именно этот creator создал ее, ID/config совпадают и сеть больше никем не используется. Ранее существовавшая пустая kind-сеть сохраняется с исходным полным хешем. Непустая сеть блокирует создание или cleanup; disconnect, name-only kind delete и глобальный prune отсутствуют. Подтверждение завершения включает независимое сравнение исходного baseline; автоматическое восстановление контекста прерванного creator не выполняется.
