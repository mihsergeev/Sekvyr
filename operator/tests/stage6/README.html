Этап 6: отдельный испытательный контур

Исходники подготовки не означают успешный E2E. Здесь не заявляются production readiness, физическая независимость хранилища или защита от удаления самого trial PVC. Установка и серверные команды выполняются только после сигнала координатора.

Зафиксированный storage backend

SeaweedFS 4.51, commit 153ab668c99731a6d29492bf6c61d0b4fa701101. Официальный multi-arch образ:

ghcr.io/chrislusf/seaweedfs@sha256:f7a49e3f3972ebed5be2ed4befa4a0c68eb7bdddba6e692d42729ceb545134b8

Linux/amd64 manifest: sha256:3a522c379599e163433a636e75022630848b63a74f08ea37bf06f8d776e9a707. Сверены GitHub release, официальный workflow и совпадающие registry manifests GHCR/Docker Hub. Релиз.

Границы доступа

Создаются семь новых namespace: storage, gateway, witness, fencer, apps, panel и foreign. Только отдельный JournalGateway получает upstream AWS credentials. Witness и fencer используют custom slots API по mTLS; их identities не содержат storage key. Offline storage admin применяется только к одноразовому trial bucket и fault injection.

В текущем Enrollment fencer и operator находятся в одном installation namespace apps, с разными закрепленными ServiceAccount UID и credentials. Зарезервированный namespace fencer остается пустым. Два экземпляра каждого процесса на одной ноде проверяют конкуренцию и повторное чтение журнала, но не физическую независимость fault domains.

Default-deny NetworkPolicy действует до создания workloads. У upstream ingress разрешены одновременно точный namespace gateway и роль pod; две selector-записи внутри одного peer означают AND. Прямой API filer/volume не публикуется runtime-компонентам. Реальную работу NetworkPolicy должен подтвердить сетевой отрицательный тест, одного manifest недостаточно.

SeaweedFS 4.51 поддерживает conditional PUT, но не предоставляет требуемый s3:if-none-match IAM condition context. Поэтому прямой bucket не считается immutable journal. Gateway не проксирует произвольный S3, не выдает credentials и не имеет Delete/Copy/multipart/unconditional PUT API. Его storage append принудительно использует conditional PUT и COMPLIANCE retention.

Подготовка

python3 run.py --task-dir "$TASK_DIR" --phase prepare
python3 run.py --task-dir "$TASK_DIR" --phase render --storage-class "$APPROVED_STORAGE_CLASS"
# После проверки и сигнала координатора:
python3 run.py --task-dir "$TASK_DIR" --phase infrastructure --execute \
  --storage-class "$APPROVED_STORAGE_CLASS" --node-name "$APPROVED_NODE" \
  --expected-kubernetes "$EXACT_SERVER_GIT_VERSION"

Точный scoped kubectl и kubeconfig готовятся координатором в private task directory. Namespace должны отсутствовать: adoption и apply существующего окружения отсутствуют. Ключи, пароли и CA создаются динамически в private с exclusive writes; публичный render не содержит Secret data. TLS проверяет CA/SAN, API без mTLS не заменяет клиентскую аутентификацию.

До infrastructure вызывается evidence.py --task-dir "$TASK_DIR" --phase before. Полные UID/spec фоновых workloads сохраняются только в private. После cleanup фаза after требует точного совпадения исходного baseline, готовности нод и отсутствия namespace/PV этого прогона. Новые cluster-scoped webhook/CRD и процессы проверяются отдельно; отсутствие namespace не считается их удалением.

До genesis применяется fs.configure -locationPrefix=/buckets/canonical-trial-ledger/ -fsync=true -volumeGrowthCount=1 -apply и проверяется effective rule. Малый испытательный PVC не использует стандартное выделение семи volumes за раз. TTL не задается. Затем включаются versioning и COMPLIANCE retention. Marker storage-ready появляется только после успешных проверок, bootstrap не переинициализирует существующий marker.

Storage conformance

storage_probe.py использует официальный boto3 SDK, не собственную реализацию SigV4. После явного bootstrap два независимых S3 gateway-процесса одновременно создают один slot. Проверяются один победитель, одна version, точные bytes, retention и отказ удаления retained version. Отдельная фаза сверяет ту же version после перезапуска компонентов. Это не испытание потери питания и не доказательство нескольких fault domains.

gateway_probe.py, witness.py и dependency_cases.py используют настоящие JournalGateway/fencer API: проверяют закрытые unsafe routes, права mTLS profiles, version/delete-marker fault injection, рестарт и недоступность зависимостей. Фактические результаты конкретного прогона сохраняются отдельно; наличие helper не означает его успешный запуск.

witness.py создает два отдельных canonical witness процесса. В runtime registrations входят только основной и специальный CAS-журнал; журналы с намеренно созданными duplicate version/delete marker исключены. Конкурентный тест посылает два различных подписанных authority transition с одним expected cursor и требует ровно один HTTP 200, один 409 и одинаковый replay обоих экземпляров.

fullstack.py резервирует приложение с replicas=0 и предполагаемым initial checkpoint, затем требует реальной публикации снимка в журнал. Предполагаемый pin сам по себе не разрешает запись: подписанная инициализация и Go reader должны проверить канонический снимок. Recovery получает тот же нормализованный installation.json из Helm render, что и runtime. Повторная полная подготовка после частичного сбоя запрещена; отдельное продолжение требует проверки уже созданных UID.

Поздний уже разрешенный запрос

admission_relay.py — отдельный harness-only TLS relay, не обход product admission. Он передает AdmissionReview настоящему fencer, получает его разрешение и только затем задерживает один точный запрос: Pod UID, ServiceAccount UID/username, target UID, namespace/name, kind и resourceVersion должны совпасть. Отказ никогда не превращается в allow. Новые owner/barrier запросы проходят к настоящему admission без задержки.

Задерживается только уникальный внешний запрос с новым marker, отсутствующим у oldObject. Relay receipt должен точно совпасть с marker/resourceVersion и UID отправителя/объекта; Future обязан оставаться pending до освобождения. После завершенного takeover тест освобождает сохраненный ответ через файл /state/release только в своем relay pod. Старый запрос должен получить HTTP 409 API server по UID/RV. Timeout либо более ранний 409 не засчитываются. На диск попадают только opaque pins, тело AdmissionReview с Secret values не сохраняется.

Для ограниченного stop-the-world сценария ha_cases.py использует RuntimeTaskControl: отдельный watchdog приостанавливает только точный собственный containerd task с проверкой Pod UID, CID, immutable image content, PID/starttime/argv и node. Старый task остается живым. После подтвержденного PAUSED разрешена явная fault injection: только duration собственного Lease меняется с 15 на 2 секунды через UID/RV/holder/renewTime tests. Другой экземпляр должен самостоятельно получить Lease с обычными 15 секундами, текущие signed grant/activation и все object barriers. Это не доказательство естественного 15-секундного failover или сетевой partition. В finally восстанавливается только duration, если она осталась 2; старые holder/renewTime не возвращаются.

Полная цепочка и recovery

После Coordinator.prepare() и initialize_and_start() отдельно вызываются Application.basic_rollout_cases(coordinator), DependencyCases и HACases. Повтор подготовки не используется как исправление теста. RollbackCases восстанавливает старые байты protected state через новый Kubernetes resourceVersion, а также меняет только derived panel index. Это не raw etcd rollback и не испытание подмененного ciphertext сервера.

adapter = RecoveryAdapter(coordinator, reviewed_active_values,
    pinned_image, task / "helm", task / "chart", approved_node)
# Только после явной fault injection missing state и проверки fail-closed:
adapter(coordinator.protocol, exact_saved_current, 2)
# RotationCases получает отдельно проверенную текущую authority после enrollment.
# Witness callback: rotate_witness(coordinator, next_protocol, exact_state).
# Final callback: adapter(next_protocol, exact_state, 3).

RecoveryAdapter сохраняет точные signed input/cursor/plan и encrypted export до эффектов, создает новые bootstrap refs и требует подписанной завершенной recovery. После возобновления двух operator/fencer нужен новый lastSuccessfulSyncTime, точный current checkpoint и отсутствие исторического rollout. RotationCases последовательно меняет publisher/read/witness/admin/fencer/node keys, проверяет отказы старых ключей и отдельный нормальный rollout после final recovery. Offline keys не берутся из panel discovery.

До cleanup вызывается log_privacy.scan(coordinator). PASS требует complete=true и confirmedLeaks=0 для доступных current/previous logs только своих закрепленных Pods и публичных status двух CR. Проверяются все известные старые/новые fixture secrets и canaries; в evidence попадают только counts. Это не утверждение о недоступных исторических rotated logs.

Уборка

UID namespace и заранее разрешенных cluster-scoped manifests сохраняются сразу из CREATE responses. Перед namespace сначала удаляются собственные ValidatingWebhookConfiguration, ClusterRoleBinding и ClusterRole с проверкой UID/структуры. Затем удаляются namespace, и только после их исчезновения — свои CRD при отсутствии любых CR. Namespace cleanup отказывается работать, пока закрепленные webhook/RBAC существуют: fail-closed webhook не должен заблокировать garbage collection.

Удаление использует raw DELETE с server-side UID precondition. Смена UID, неполные pins и отсутствие специального подтверждения уничтожения trial storage запрещают удаление. Accepted DELETE не считается завершенной уборкой: отдельно проверяются отсутствие namespace/PV, cluster-scoped trial webhooks/CRD, фоновые workload UID/spec и scoped процессы.

python3 run.py --task-dir "$TASK_DIR" --phase cleanup
# Только после сохранения безопасного evidence и разрешения координатора:
python3 run.py --task-dir "$TASK_DIR" --phase cleanup --execute \
  --acknowledge-trial-storage-destruction

Удаление disposable PVC уничтожает и COMPLIANCE-объекты через администрирование нижнего хранилища. Это осознанная граница испытательного профиля, а не доказательство производственного WORM. Cluster-scoped cleanup — отдельные фазы cleanup-cluster-before и cleanup-cluster-after, с отдельными creation UID pins; неизвестные cluster resources не принимаются под управление.
