Эксплуатация и безопасное восстановление

Документация неопубликованных operator/chart/provision 0.1.0-rc.1 и matching backend 1.1.0-rc.1. Подставьте рассмотренные version/digest/checksum; новые RC не наследуют живую приемку старого digest. Опубликованная панель 1.0.3 не поддерживает E2E2 API; agent 1.0.3 неизменен. Offline команды sekvyr-provision bootstrap/recovery и native checkpoint-recovery сейчас HA E2E2-only. Установка содержит полный порядок с reservation/seal; собственный signer не требуется.

1. Проверяйте данные отдельно от Pod Ready

kubectl get sekvyrsecret application-runtime -n secret-sync \
  -o jsonpath='{.status}'
kubectl get sekvyrstore application-secrets -n secret-sync \
  -o jsonpath='{.metadata.uid}{" "}{.metadata.generation}{"\n"}'

Сверьте current CR generation, Store UID/generation, timestamp новой попытки и lastAttemptTime == lastSuccessfulSyncTime. Для E2E2 нужны актуальные Ready/BootstrapReady/WitnessReady/DataCurrent/RolloutReady и точный verified checkpoint; Plain использует WitnessReady Unknown/NotApplicablePlain, без checkpoint. Один kubectl wait на старый True не доказывает новый sync после upgrade или отказа. Проверяйте новые значения внутри приложения приватным canary, не печатая их в журналы/Events/report.

Operator /healthz//readyz — process probes. Fencer /readyz выполняет свежую онлайн-проверку журнала, /healthz — process-only. Chart fencer readiness timeout по умолчанию 10 с, допустим 1..30; это не разрешение кешировать trust или обходить отказ. Clock backstep/future Lease не исправляют увеличением допуска или сбросом state.

При sealed, timeout, отказе API, 401/403 и cryptographic failure сохраняются последние хорошие Secret и приложение; ошибка отражается в status. Это доступность уже выданных данных, не мгновенный отзыв. Не возобновляйте pending rollout до новой успешной проверки источника. StateMissing/StateReplaced, RecoveryPending и TargetMissing/TargetReplaced требуют разбора; не удаляйте state и pins ради повторного запуска.

2. Включение rollout: три явных разрешения

  1. В полном административном values: sync.enabled=true, rollout.enabled=true, точный непустой rollout.allowedDeployments.
  2. В выбранном Store binding — точный rollout.allowedDeployments, в пределах административного списка.
  3. В SekvyrSecret — spec.rollout.enabled=true и явный список deployments, разрешенный binding. Сами Deployment должны уже существовать, иметь известные UID и использовать выбранный Secret.
# Фрагменты разных документов, не один values-файл:
# Helm values:
sync: {enabled: true}
rollout: {enabled: true, allowedDeployments: [sample-api]}
# Store binding:
rollout: {allowedDeployments: [sample-api]}
# SekvyrSecret.spec:
rollout: {enabled: true, deployments: [sample-api]}

Изменение values выполняйте рассмотренным native Helm upgrade; изменение Store/CR — только владельцем с проверкой UID/resourceVersion. Не расширяйте список селектором или wildcard. Начальное создание, equal plaintext и само включение opt-in не создают исторический restart. Реальное изменение пишет opaque revision и durable intent; Debouncing ожидаем, DeploymentPaused удерживает pending. Оператор меняет только собственную аннотацию Pod template secrets.sekvyr.ru/restart-<targetSecretUID> через UID/RV CAS. Deployment recreation не усыновляется автоматически.

Secret volume обычно может обновиться без рестарта, если приложение читает проекцию kubelet без subPath. EnvFrom не меняет окружение уже запущенного процесса. Согласуйте внешний reloader отдельно: в испытании только свои Deployment отключали его тремя reloader.stakater.com/auto, secret.reloader.stakater.com/auto, configmap.reloader.stakater.com/auto со значением "false". Глобальный контроллер не менялся. Exactly-once restart при сторонних writers не обещается.

3. Что резервировать

Publisher AES/signing и независимый admin keyУ доверенных владельцев, отдельно от панели и operator backup. Без private key или допустимого независимого recovery-процесса новый wrap/подпись не возникают.

Согласуйте окно: остановите административные публикации/ротации, дождитесь текущего подтвержденного состояния, затем зафиксируйте связанные receipts. Если нужны raw Kubernetes exports, пишите их только в приватный каталог mode 0700 с umask 077 и шифруйте backup. Не выводите Secret YAML в терминал/тикет/CI; base64 не шифрование. Target Secret содержит plaintext и требует той же защиты.

Протестируйте восстановление в отдельном контуре. Trial SeaweedFS с retention и fsync не доказывает независимые production fault domains, WORM против root или power-loss durability. Ни replicas, ни наличие backup без проверенного restore этого не меняют.

4. Restore — не сброс checkpoint

Возвращенная из backup панель может отставать от независимого журнала. E2E2 не должен принимать ее старый index как актуальный: отсутствующий current envelope приводит к fail-closed, а не offline fallback. Возвращайте нужные encrypted artifacts по известным hashes; не переинициализируйте genesis и не уменьшайте floor. CREATE старого Kubernetes имени получает новый UID, поэтому старые pins нельзя исправить простым копированием YAML.

HA state loss / node replacement: остановите всех старых operator writers. В trial chart это ha.maintenance=true, replicas=0; fencer остается >=2. Дождитесь физического исчезновения старых Pod, а не только Deployment Ready. Сохраните старые generation/state UID и последнюю проверенную цель. Заранее создайте новые immutable identity/trust и новый mutable state под новыми именами/UID; marker указывает новую bootstrap generation. Не перехватывайте существующую цель с чужим UID.

  1. Независимый администратор подписывает enrollment/reconfiguration по текущей authority и точным namespace/SA/Lease/material/object UID. Old grants становятся неактивны; новый grant не активен до всех барьеров.
  2. Подготовьте новый strict trust, current envelope/wrap и signed recovery plan operation=recover. В нем exact cursor/snapshot, previous generation/state UID, новая большая generation/new state UID, node/trust pins, Store/CR generations, target UID и ожидаемый hash текущих raw state.json bytes.
  3. Срок plan не более 24 часов и еще не истек. Администратор подписывает его текущим независимо разрешенным admin key; private key не входит в manifest. Новый marker и план не являются заменой подписи.

Подготовка плана существующим offline CLI

Используйте RecoveryRequest и контракт provision. До него повторите bootstrap для новой generation: новые настоящие UID из CREATE, trust reservation → exact UID/RV populate+immutable → независимая проверка; operator остается 0. В uid receipts/Binding и recovery.Body.Identity перенесите точный нормализованный Identity из bootstrap output; recovery не вычисляет его за вас. Подпишите и online-commit новый enrollment, затем зафиксируйте его post-enrollment chain/cursor для плана. Не смешивайте прежний body cursor с новой цепочкой.

# recover-request.json (private 0600):
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-post-enrollment-records.json",
          "expected_cursor":{"journal_sequence":"<EXACT_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "config_file":"bootstrap-next/installation.json",
 "receipts_file":"bootstrap-next/receipts.json","binding_file":"binding.json",
 "body_file":"recover-body.json","state_file":"reviewed-state-bytes.bin",
 "admin_key_file":"admin/private.pem"}
/secure/sekvyr-provision recovery --work-dir /secure/provision \
  --input recover-request.json --output recovery-next

reviewed-state-bytes.bin — точные bytes state.json, ожидаемые в новом pinned state Secret, без JSON normalization. При отсутствии этого data key сохраните явный пустой 0600 файл: для operation=recover state_file обязателен. При initialize state_file="" и SHA-256 пустых bytes. Body recovery.Body отдельно содержит previous generation/старый state UID, новые material UID, current snapshot/cursor, expiry и allow_rollout=false. Provision подписывает текущим admin и вызывает recovery.Verify; online CLI ниже использует /secure/provision/recovery-next/plan.json как --plan и bootstrap-next/installation.json как --installation-file. Это не commit receipt и не разрешение обойти online journal/witness.

export KUBECONFIG=/secure/admin.kubeconfig
/secure/sekvyr-checkpoint-recovery \
  --installation-file=/secure/provision/bootstrap-next/installation.json \
  --plan=/secure/provision/recovery-next/plan.json \
  --envelope=/secure/provision/current-envelope.json \
  --reader-wrap=/secure/provision/current-reader-wrap.json \
  --allow-trial-canonical-ledger

CLI использует encrypted offline exports, но journal/witness должны оставаться онлайн. По умолчанию rollout выключен. Для changed-data recovery он требует одновременно явного CLI --enable-rollout, соответствующей installation policy и allow_rollout=true в подписанном плане. Equal-data recovery не создает historical restart.

Prepared сохраняется до target update; затем state помечается complete. После потерянного ответа разбирают тот же plan/recovery ID и наблюдаемую фазу: нельзя генерировать новый ID или автоматически rebase на свежий cursor. Exact plan допускает проверенное продолжение; продвижение журнала может потребовать нового независимо рассмотренного плана и оставить RecoveryPending. Между journal и Kubernetes нет атомарной транзакции; lag после проверки не равен разрешению откатить уже более новую примененную цель.

Resume возможен только при сохраненных UID/context и проверенной целостности. После CheckpointRecoveryComplete подтвердите current state/target, снимите maintenance, верните две operator replicas и проверьте свежий sync. Не переносите старый pending intent в новую generation. Прежние state names/UIDs остаются в ha.webhook.retiredStateSecrets до отдельного административного cleanup; не сужайте admission scope посреди recovery.

Этот CLI требует HA E2E2 profile и не является restore-командой для Plain или non-HA state loss. Для них автоматического восстановления потерянного high-water state нет: остановите writers, сохраните target, рассмотрите восстановление исходного объекта/backup либо отдельную миграцию с новым target и bootstrap. Нельзя очистить bindings, снять UID pin или принять чужой Secret, чтобы скрыть потерю состояния.

5. Ротации

Что меняетсяПорядок
Projected JWT / JWKSФайл token обновляет kubelet в том же Pod; не записывайте JWT руками. Signer rotation отдельно: независимо подготовленные old+new public keys, overlap в offline JWKS панели, настоящий new-kid token, затем retirement при обоих еще valid JWT (запас >30 с). Новые обмены старого kid должны дать 401. Это не немедленный отзыв machine sessions/удаленных Pod.
Node P256Остановить старых writers, подготовить один новый key на все replicas, независимо подтвердить public fingerprint, передать public key панели, выдать новые signed wraps всех разрешенных views. Смена public_key удаляет прежние machine wrappers; нельзя чередовать старый и новый key между репликами. Затем новая enrollment/bootstrap generation и signed recovery с exact pins.
AES read keyОтдельная cryptographic rotation: новый epoch, заново зашифрованный полный snapshot и новые wraps, signed authority transition/activation. Rewrap для нового node при прежнем AES — не смена project key. Старый read key должен перестать расшифровывать новые snapshots.
Publisher / witness / fencer / adminНовая public authority подписывается текущим разрешенным admin по CAS/current cursor. Epoch/revision, signer material, independent pins и service rollout переключаются согласованно; при witness rotation обновляется и pin панели. Authority change инвалидирует старый grant, новый требует barriers. Утрата admin private key не исправляется доверенным ключом из самой панели.
TLS / CAПроверенный cert с правильными SAN, новый immutable Secret/ConfigMap и точные UID/hash refs. Не заменяйте CA lookup или отключением TLS verification. Обычная TLS ротация не разрешает смену publisher/witness authority.

Ротация AES/node поколения 2 проверена в этапе 7 на конкретном amd64 образе; все-все ротации и новые RC требуют собственных сценариев. Legacy E2E1 не получает E2E2 migration автоматически: используйте отдельно рассмотренный publisher migration с новым canonical snapshot, не сброс trust. На trial control plane API restart может оборвать panel port-forward; будущий coordinator hook переподключает только свой transport после Ready/crypto checks. Исторический прогон с ручным продолжением не является проверкой нового hook.

Offline подготовка ротации

keygen создает только одну новую роль за вызов. Для AES используйте role=read с новым output; epoch bump при прежнем AES не отзывает старый node. snapshot с pending=true подготавливает следующий полный envelope/wrap без record.json; затем transition подписывает существующий TransitionBody с activating_envelope и проверяет candidate Replay. rotate-read-key требует action=rotate-read-key и следующего read epoch; rotate-publisher — action=update, следующего policy epoch и новых publisher public keys. Restore — отдельный kind=recover с проверенной history/recovery_from, не снижение sequence. Rotate-admin/witness/fencer используют соответствующий закрытый kind и текущий admin, без лишнего activating snapshot.

/secure/sekvyr-provision snapshot --work-dir /secure/provision \
  --input reviewed-pending-snapshot.json --output pending-rotation
/secure/sekvyr-provision transition --work-dir /secure/provision \
  --input reviewed-transition-request.json --output signed-rotation

Запросы имеют те же обязательные поля, что в установке; transition request ссылается на отдельный точный BodyFile. Нельзя выдать pending за опубликованный current. Online CAS, согласованная смена signer/pins и независимые receipts обязательны. Wrapper-only команды нет: для node rotation через этот CLI подготовьте новый AES/read epoch и следующий полный snapshot с wrap для нового node, затем admin transition/enrollment и signed recovery. Собственный signer не нужен. Остальные authorized readers также должны получить проверенные wraps; инструмент не управляет их online grants. Сохраняйте точные ciphertext/plan outputs для lost-ack разбора: новый запуск snapshot создает новые salt/nonce и другой hash.

6. Upgrade и ограниченный rollback

  1. Выберите точный reviewed chart version и image digest, проверьте совместимость backend/protocol/state. Сохраните текущие manifests, CRD schemas, values, external UID receipts, journal cursor и backup. В namespace не должно быть параллельного административного writer.
  2. Рассмотрите schema diff CRD отдельно. Helm upgrade не обновляет CRD из crds/ автоматически. Администратор отдельно применяет рассмотренную additive schema с сохранением существующих CR; проверяет pruning, validations и stored versions.
  3. Сделайте полный render новых values; сравните RBAC, webhook, material refs и Pod templates. Не используйте reuse-values как замену review. В текущем chart resources общие для operator и fencer: memory change может заменить обе пары.
CHART='/secure/sekvyr-operator-<REVIEWED_VERSION>.tgz'
helm template secret-sync "$CHART" --namespace secret-sync \
  -f /secure/next-values.yaml > /secure/next-render.yaml
helm upgrade secret-sync "$CHART" --namespace secret-sync \
  -f /secure/next-values.yaml --skip-crds --wait --timeout 180s

После Ready дождитесь физического исчезновения прежних измененных Pod UID. Зафиксируйте UTC cutover и прежний lastSuccess; требуйте новую успешную попытку после cutover с current CR/Store UID/generation и checkpoint, затем проверьте приложение. Не публикуйте новый head только ради маскировки старого status.

Helm rollback откатывает manifests, а не journal, CRDs, keys или data. Команда helm rollback secret-sync <REVIEWED_HELM_REVISION> --namespace secret-sync --wait --timeout 180s допустима только после подтверждения, что старые binaries понимают текущие CRD/state/authority и сохраняют текущие pins/floors. После новой bootstrap generation или несовместимого wire автоматический rollback не поддерживается: нужен forward fix либо отдельно подписанная миграция. Retained ConfigMap сверяется по известному UID и точным bytes, а не принимается по имени.

CRD rollback не является частью Helm rollback. Более старая schema может удалить неизвестные поля/prune данные, отвергнуть existing CR или не понимать stored version. Не удаляйте CRD для downgrade: это cluster-wide удаление CR во всех namespaces, возможно с GC целей по Delete policy. Без отдельно проверенной schema/data migration такой downgrade не заявляется безопасным.

7. Uninstall и сохранение данных

Выбирайте deletionPolicy: Retain при создании binding; policy неизменяема. Для существующего Delete нужен отдельный план миграции/сохранения данных, не patch policy и не снятие ownerReference наугад. Сам chart не управляет target/identity/trust/state Secrets или внешними SA/Lease. Удаление CR при Delete может удалить target через GC, хотя оператор не имеет Secret DELETE. Удаление namespace удалит и Retain-данные.

  1. Остановите публикации и явный rollout request/suspend согласно рассмотренному плану. HA: maintenance=true/replicas=0, дождаться отсутствия старых operator Pod; fencer/admission не отключать до остановки writers. Non-HA: сначала одновременно sync.enabled=false и rollout.enabled=false в полном reviewed values, затем дождаться ухода старых sync-enabled Pod.
  2. Проверьте current target UID/данные/приложение и backup. Удалите только выбранный captured release; не удаляйте общий namespace/CRD.
helm uninstall secret-sync --namespace secret-sync --wait --timeout 180s

Проверьте исчезновение только своих Deployment/Role/RoleBinding и HA cluster resources, сохранность external pins и target. configuration.retain=true оставляет immutable ConfigMap revisions: после отсутствия всех consumers удаляйте только рассмотренные объекты с DeleteOptions UID preconditions. Наличие keep не дает права заново усыновить объект или откатить trust. CRD, Store/CR и ключи удаляются отдельным согласованным lifecycle с учетом других установок.

Проверьте отсутствие собственных port-forward/helper процессов и утекших temporary credentials; сравните независимый baseline чужих workloads, volumes, networks и host state. Не используйте global prune. В этапе 7 строгий Docker resource audit прошел, а глобальный IPv6 audit имел явно принятое пользователем исключение; точное восстановление всего хоста не заявлялось. Перед новым trial нужны исходные sysctl/IPv6 anycast/address flags/firewall/routes и полный image inventory.

Пределы и совместимость

Фактически испытаны Linux amd64, 960d на Kubernetes 1.34.1+k0s и d328 на kind 1.37.0; последний d328/timeout-10 не перепроверен на 1.34. ARM64 и новые RC пока не получают этого покрытия. Backend 3e25 этапа 7 имел 9 открытых HIGH OS CVE, 45 matches, без доказательства exploitability или waiver; новое исправление требует нового scan/acceptance.

Production WORM/независимые fault domains, cross-object/system atomic freshness, exactly-once restart и защита от Byzantine control plane/storage, root-компрометации или etcd resourceVersion rewind при старом запросе не обещаются. В E2E2 plaintext read key, пароль проекта и publisher private key не передаются панели. Компрометация trusted publisher/browser JavaScript или чтение plaintext в Kubernetes находится в границе доверия.
