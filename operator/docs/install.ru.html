Установка и независимый bootstrap

Документация релиз-кандидата. Оператор, чарт Helm и офлайн-инструмент sekvyr-provision: 0.1.0-rc.2; соответствующий сервер панели: 1.1.0-rc.4. Подставьте проверенную версию чарта вместо <REVIEWED_VERSION> и дайджест проверенного образа вместо <REVIEWED_DIGEST> (sha256: и 64 шестнадцатеричных символа). Отдельно проверьте контрольную сумму sekvyr-provision. Опубликованная панель 1.0.3 не поддерживает новый API E2E2. Подписанный агент 1.0.3 остается без изменений.

1. Выберите профиль и границы доверия

ПрофильЧто требуетсяЧто не обещается
Plain, без HAЯвный Plain binding, закрепленная TLS-панель, новая авторизация, полный проверенный ответ, административные identity/trust/state.Подлинность издателя независимо от панели, anti-rollback, witness freshness, HA fencing.
E2E2, без HAПодписанные snapshots и read wraps, независимо закрепленные publisher/witness keys и положительный minimum checkpoint, постоянный state.HA fencing или автоматическое восстановление потерянного state.
E2E2 HA trialПредыдущие условия + отдельный canonical journal/gateway, fencer/admission, signed enrollment и initialize/recover, все цели заранее созданы и UID-pinned. Одна установка — один log/view.Production WORM, независимые fault domains, HA для Plain или безопасность при Byzantine/root-компрометации.

По умолчанию sync.enabled=false, rollout.enabled=false, ha.enabled=false. Sync и rollout включаются отдельно. Pod Ready означает готовность процесса: актуальность данных проверяют по CR status и фактическому приложению.

2. Подготовьте namespace, TLS и права

Одна установка работает в одном доверенном административном namespace. Запретите посторонним создавать Pod и изменять bootstrap, Store, CR, target и ServiceAccount: доступ к Pod/Secret может раскрыть ключи и уже расшифрованные данные. Non-HA sync имеет namespace-scoped Secret CREATE, который Kubernetes RBAC не умеет ограничить по имени; runtime дополнительно проверяет allowlist и ownership. HA не имеет CREATE Secret. Secret list/watch/delete и Pod delete оператору не требуются; Deployment get/patch появляются только с rollout opt-in.

К запуску runtime подготовьте namespace и три разных Opaque Secret: immutable P256 identity, immutable trust, mutable state. Для HA trust сначала резервируется, затем заполняется и становится immutable по церемонии раздела 6, пока operator остановлен. Сохраните UID из ответов CREATE. Замена объекта под тем же именем не сохраняет его identity. Не передавайте private keys, JWT, пароли или содержимое trust в Helm values: values входят в историю release. Для внешних SA/Lease задайте create=false и известные UID; chart не делает lookup/TOFU и не принимает их под управление Helm.

Готовый sekvyr-provision подписывает артефакты существующего протокола; писать собственный signer не требуется. Файловые команды поддерживают Linux. Заранее подготовьте принадлежащий текущему UID приватный каталог /secure/provision mode 0700. Все входы и вложенные каталоги приватны, пути в JSON относительны этому каталогу, файлы обычно 0600. Symlink, hardlink, FIFO, выход за каталог и перезапись запрещены. Существующий output, включая частично записанный, требует разбора и не усыновляется повторным запуском.

# keygen-node.json (private 0600):
{"role":"node"}
/secure/sekvyr-provision version
/secure/sekvyr-provision keygen --work-dir /secure/provision \
  --input keygen-node.json --output node
# node/private.pem: P256 PKCS8; node/public.json: public fingerprint.
# public-node.json: {"role":"node","private_file":"node/private.pem"}
/secure/sekvyr-provision public --work-dir /secure/provision \
  --input public-node.json --output node-public-copy

Для HA ceremony независимо выполните keygen с одной ролью за вызов: admin, publisher, witness, fencer, read; каждому запросу и output задайте новое имя. Ed25519 роли дают private.pem/public.json, read дает только read-key.bin (32 случайных байта). Не собирайте все роли на сервере: команды выполняют соответствующие владельцы, передают только нужные public/ciphertext artifacts. Не генерируйте новый node при восстановлении прежней identity. Private manifests, plaintext и CREATE receipts остаются вне Git, shell history и Helm values. Для Plain/non-HA keygen/public также пригодны, но bootstrap/recovery ниже требуют HA.

Node fingerprint — p256-sha256: + SHA-256 SEC1 uncompressed public point (65 bytes), не хеш PEM или SPKI. Все реплики используют один закрепленный node key. TLS origins — точные HTTPS origins без credentials/path/query/fragment. Пользовательские CA задаются immutable ConfigMap с UID и derSetSHA256 по алгоритму installation, не хешом текста PEM. Отсутствие CA reference использует system roots. Fencer admission certificate должен включать DNS service.namespace.svc; одного .svc.cluster.local недостаточно.

Разрешите только нужные DNS и направления: operator → Kubernetes API/panel; E2E2 → witness; HA operator/fencer/witness → gateway; gateway → storage; API server → admission. У inter-namespace peer namespaceSelector и podSelector соединяются в одном peer (AND); API/admission IP paths отдельно закрепляются точными IP/портами. Chart не устанавливает NetworkPolicy. Проверяйте реальные разрешенные и запрещенные соединения; port-forward и наличие YAML не доказывают CNI isolation.

3. Bootstrap Plain

Зарегистрируйте в панели независимо полученные issuer, audience sekvyr, public JWKS; выдайте machine identity namespace + SA name только нужный environment/path. Backend использует offline JWKS, а не TokenReview. Runtime SA UID pins — отдельная проверка; удаление Pod не отзывает JWT мгновенно. E2E-проект не допускается как Plain.

Данные immutable trust Secret для чистого Plain строго имеют форму ниже. Этот JSON не подписывается автоматически: его доверие обеспечивают независимая подготовка, разрешенные origins и точный immutable Secret UID.

{
  "schemaVersion": 1,
  "protocol": "plain-v1",
  "installationID": "<INSTALLATION_UUID>",
  "bootstrapGeneration": 1,
  "namespace": "secret-sync",
  "serviceAccount": "operator-reader",
  "panelOrigin": "https://panel.example.invalid",
  "nodePublicKeyFingerprint": "p256-sha256:<PUBLIC_POINT_SHA256>"
}

В mutable state Secret ключ installation.json содержит только installationID и bootstrapGeneration. Для новой non-HA установки второй ключ state.json:

{"version":1,"installationID":"<INSTALLATION_UUID>","bootstrapGeneration":1,
 "trustBundleUID":"<TRUST_SECRET_UID>",
 "nodeFingerprint":"p256-sha256:<PUBLIC_POINT_SHA256>","bindings":{}}

Не используйте этот пустой state для восстановления прежней установки. В HA initialize второй ключ первоначально отсутствует: его создаст только рассмотренный signed recovery, описанный ниже.

4. Values и первый CR

Сохраните полный рассмотренный values-файл приватно. Ниже минимальная non-HA Plain конфигурация с внешними SA и Lease; отсутствующие параметры берутся из рассмотренного chart.

image:
  repository: ghcr.io/mihsergeev/sekvyr-operator
  digest: "<REVIEWED_DIGEST>"
replicas: 1
serviceAccount: {create: false, uid: "<SA_UID>"}
leaderElection: {id: operator-leader, create: false, uid: "<LEASE_UID>"}
configuration: {retain: true}
sync: {enabled: true}
rollout: {enabled: false, allowedDeployments: []}
ha: {enabled: false}
installation:
  installationID: "<INSTALLATION_UUID>"
  namespace: secret-sync
  serviceAccount: operator-reader
  bootstrapGeneration: 1
  allowedPanelOrigins: ["https://panel.example.invalid"]
  allowedWitnessOrigins: []
  identityKeySecret: {name: operator-node, uid: "<NODE_SECRET_UID>", key: node.key}
  trustBundleSecret: {name: operator-trust, uid: "<TRUST_SECRET_UID>", key: trust.json}
  stateSecret: {name: operator-state, uid: "<STATE_SECRET_UID>", key: installation.json}
  protectedSecretNames: []
  protectedSecretUIDs: []
  protectedPrefixes: [sh.helm.release.v1.]
  caConfigMaps: []
  allowedTargetSecrets: [application-env]

Администратор устанавливает только рассмотренные CRD secrets.sekvyr.ru/v1alpha1. Helm install ставит CRD из chart, если их еще нет; upgrade не является процедурой обновления CRD. Для уже администрируемых CRD используйте --skip-crds. До install проверьте отсутствие release и его новых имен; не применяйте take-ownership/force.

CHART='/secure/sekvyr-operator-<REVIEWED_VERSION>.tgz'
helm show chart "$CHART"
helm lint "$CHART" -f /secure/operator-values.yaml
helm template secret-sync "$CHART" --namespace secret-sync \
  --include-crds -f /secure/operator-values.yaml > /secure/reviewed-render.yaml
# Рассмотреть CRD, RBAC, refs, immutable ConfigMap и полный Pod template.
helm install secret-sync "$CHART" --namespace secret-sync \
  -f /secure/operator-values.yaml --wait --timeout 180s

После появления CRD создайте Store, затем перенесите его UID из сохраненного CREATE receipt в SekvyrSecret. Не копируйте fictional UID из design examples.

apiVersion: secrets.sekvyr.ru/v1alpha1
kind: SekvyrStore
metadata: {name: application-secrets, namespace: secret-sync}
spec:
  endpoint: {url: https://panel.example.invalid}
  bindings:
    - id: "<BINDING_UUID>"
      name: runtime
      resourceName: application-runtime
      source: {group: demo, project: sample, environment: trial, pathPrefix: /runtime}
      selection: {mode: All}
      encryption: {mode: Plain}
      target: {name: application-env, type: Opaque, deletionPolicy: Retain, allowEmpty: false}
      rollout: {allowedDeployments: []}
---
apiVersion: secrets.sekvyr.ru/v1alpha1
kind: SekvyrSecret
metadata: {name: application-runtime, namespace: secret-sync}
spec:
  storeRef: {name: application-secrets, uid: "<STORE_CREATE_UID>"}
  binding: runtime
  refreshIntervalSeconds: 60
  suspend: false
  rollout: {enabled: false, deployments: []}

Применяйте эти документы отдельно: UID Store еще не существует до CREATE. Проверяйте observedGeneration, observedStoreUID/Generation, свежие lastAttemptTime == lastSuccessfulSyncTime и DataCurrent. Для Plain WitnessReady=Unknown / NotApplicablePlain, checkpoint отсутствует. Только после этого запускайте потребителя envFrom; volume reload должен читать каталог целиком без subPath и не смешивать поколения.

5. Независимый bootstrap E2E2 и read wraps

  1. Доверенный publisher хранит AES read key отдельно от Ed25519 signing key. Operator получает только read key через signed encrypted wrapper для своего P256 node key. Пароль проекта и publisher private key серверу/оператору не отправляются. Общий writer password дает криптографическую способность подписывать каждому его владельцу; роль UI не отменяет ее.
  2. По независимому каналу подтвердите publisher/witness/admin public keys и fingerprints, scope realm/project/environment/view/log, genesis hash и положительный minimum checkpoint. Не получайте первый trust из той же потенциально подмененной панели. Скомпрометированный publisher JavaScript тоже находится в границе доверия.
  3. Соберите strict schemaVersion 2 trust по actual wire: installation/node pins и viewTrust, привязанный к Store UID + binding ID. Public design example не является deployable trust: поля description/exampleOnly и placeholders не проходят strict parser.
  4. В unreleased panel создайте view; передайте publisher-signed полный encrypted snapshot, а не отдельный key patch. После канонического commit и fresh witness proof индексируйте hash. Owner выдает signed reader wrap конкретной machine; одновременно нужны разрешение whole environment/path и explicit view grant. API /api/e2e2/views, /envelopes, /index, /readers не приписываются panel 1.0.3.
  5. Для отдельного нового E2E2 binding используйте {mode: E2E, protocol: e2e2, trustKey: runtime-view, freshness: {mode: WitnessCurrent}} и source.viewId. Encryption/trust reference существующего binding неизменяемы: это не patch прежнего Plain binding. Установка разрешает точные panel/witness origins и CA. E2E1/offline/polling fallback нет.

Используйте sekvyr-provision: контракт команд, точные JSON request types. keygen/public готовят ключи; genesis/snapshot/transition создают подписанные offline artifacts. bootstrap/recovery сейчас требуют HA E2E2 config: это не Plain/non-HA installer или lost-state restore. Non-HA использует strict trust/state wire и отдельно рассмотренную административную установку. Harness keys/vectors остаются публичными fixtures; готовая UI-кнопка bootstrap не обещается.

6. HA trial: от offline genesis до первого sync

Одна установка обслуживает один log/view. Ниже порядок для новой generation 1, не процедура восстановления старого state. Команды provision не вызывают сеть, Kubernetes или storage commit. Все показанные request-файлы и вложенные protocol bodies подготовьте приватно до вызова; подставьте рассмотренные значения. Все поля request обязательны, включая pending и пустой state_file; nullable protocol union fields остаются явными null. Дубликаты, неизвестные поля и неверный регистр отвергаются.

6.1. Genesis и независимый pin

Подготовьте genesis-body.json по journal.GenesisBody / Authority: format=sekvyr-journal-genesis-v1, точный scope из пяти UUID, panel_origin, начальная authority revision/epochs, отдельные public admin/publisher/witness/fencer keys и recovery_from=null для нового log. У journal.Key только key_id/public_key, не весь provision public descriptor. Genesis подписывает независимый admin, не панель.

# genesis-request.json
{"body_file":"genesis-body.json","admin_key_file":"admin/private.pem",
 "admin_public_file":"admin/public.json"}
/secure/sekvyr-provision genesis --work-dir /secure/provision \
  --input genesis-request.json --output genesis

Выходы: record.json, records.json и registration.json. Genesis проходит Sign → Replay. Независимо подтвердите original admin public key, log ID, genesis hash и minimum cursor; сохраните reviewed-registration.json отдельно от сервера. Для нового log floor может указывать genesis sequence 0, но runtime trust потребует положительный snapshot. Зафиксируйте каждый последующий floor по отдельному проверенному receipt; никогда не снижайте его по ответу панели.

Отдельно разверните рассмотренные gateway/storage и witness с TLS/mTLS и собственными service identities. Operator не получает upstream S3 credential или admin key. Actual initialization CLI:

/secure/sekvyr-witness canonical-init \
  --config /secure/canonical-witness.json \
  --registration /secure/provision/genesis/record.json \
  --allow-trial-canonical-ledger

Это уже online административная команда, не часть offline provision. Сохраните CAS receipt и полный подписанный chain от genesis. При потерянном ответе сначала выясните результат прежнего CAS, не повторяйте новый init. Для каждой следующей команды укажите independently reviewed registration, полный bounded массив Record и точный ожидаемый final cursor:

"chain": {
  "registration_file": "reviewed-registration.json",
  "records_file": "reviewed-complete-records.json",
  "expected_cursor": {"journal_sequence":"<DECIMAL_SEQUENCE>",
                      "record_hash":"<EXACT_RECORD_HASH>"}
}

Не подставляйте CurrentState JSON вместо массива signed records. Provision проверяет signatures, непрерывность, hash floor на его позиции и exact final cursor. Он не узнает, что в живом журнале уже существует более новый head; online CAS/floor gates остаются обязательными.

6.2. Первый полный snapshot и read wrap

В matching backend зарегистрируйте view и machine permissions. Доверенный publisher готовит Header и Plaintext: тот же scope, первый sequence=1, previous_hash=64 нуля, action=initial, intent=publish, protocol=e2e2, suite=HKDF-SHA256+A256GCM+Ed25519, current epochs/key ID, точный entry_count, parents=[] и restored_from=null. Входной snapshot_salt задайте пустой строкой: SealSnapshot генерирует случайные salt/nonce. Values — полный JSON Plaintext с format=sekvyr-e2e2-values-v1, context и отсортированными entries path/name/value; это не исполняемый .env и не patch отдельных ключей.

# snapshot-request.json
{"pending":false,
 "chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "header_file":"header.json","plaintext_file":"values.json",
 "read_key_file":"read/read-key.bin",
 "publisher_key_file":"publisher/private.pem",
 "publisher_public_file":"publisher/public.json",
 "recipient_public_file":"node/public.json"}
/secure/sekvyr-provision snapshot --work-dir /secure/provision \
  --input snapshot-request.json --output snapshot-1

Выходы: envelope.json, reader-wrap.json, candidate.json и, при current epochs, record.json. Подпись, Decrypt и точное совпадение plaintext проверяются до записи. Wrapper шифрует AES key для явно выбранного node public key; private node/signing key и plaintext панели не передают. committed=false в candidate означает offline-подготовку, а не отказ или доказательство commit.

В panel API отдельно stage envelope, выполните canonical witness commit по exact cursor, получите fresh witness proof/index и выдайте signed wrapper конкретной machine через readers grant. Проверьте полученный hash/sequence и экспортируйте полный подписанный chain. Первый положительный canonical snapshot должен существовать до bootstrap, иначе trust с положительным minimum checkpoint не пройдет parser. Для HA используйте canonical journal profile, не development filesystem ledger.

6.3. UID receipts, reservation и unsigned bootstrap

Остановите operator: replicas=0/maintenance. Администратор создает namespace, разные SA, Lease, Store/CR, зарезервированные target и Deployment; приложение пока replicas=0. Сохраните настоящие UID из CREATE и текущие resourceVersion. Node Secret можно сразу создать immutable из готового private.pem. Для trust действует отдельная reservation/seal церемония: сначала создайте mutable Opaque reservation с реальным UID; это еще не доверенный runtime trust. State остается mutable с marker и без state.json. Фиктивный trust UID, lookup/TOFU и запуск operator с reservation запрещены.

Подготовьте config по installation.Config с HA config, CA/Secret pins и настоящими UID. В binding.json передайте одну привязку из Store в формате Go JSON. Если в target явно указано allowEmpty: false, опустите поле только в копии для CLI: Go не сериализует это значение по умолчанию. При true поле сохраните. uid-receipts.json имеет ровно {"enrollment": <journal.Enrollment>, "binding": <recovery.Binding>}. В Enrollment включите весь точный canonical-sorted AllowedObjects набор, разные SA/UID и Lease ref; в Binding — Store/CR names/UID/generations, binding/view/target и Identity. Только для bootstrap разрешена явная пустая Identity: инструмент вычислит существующий Go JSON BindingIdentity. Это не JCS и не подпись.

# bootstrap-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "config_file":"ha-installation-input.json","receipts_file":"uid-receipts.json",
 "binding_file":"binding.json","node_public_file":"node/public.json",
 "trust_key":"runtime-view","publisher_key_id":"<PUBLISHER_KEY_ID>"}
/secure/sekvyr-provision bootstrap --work-dir /secure/provision \
  --input bootstrap-request.json --output bootstrap-1

Полученные installation.json, trust.json, state-marker.json и нормализованный receipts.json — unsigned административные материалы. Администратор одним UID/resourceVersion CAS заполняет trust reservation точными trust.json bytes и ставит immutable=true. Затем независимо перечитывает UID, immutable, type и точные bytes; проверяет node/state/CA refs. Immutable Secret перезаписывать нельзя. UID/RV mismatch означает остановку; новый bootstrap возможен только по отдельной административной процедуре. Helm получает только refs, не эти payload/keys.

6.4. Signed enrollment, затем exact-cursor initialize

Независимый admin готовит TransitionBody: kind=enroll-installation, текущие scope/genesis/expected cursor/previous_authority_digest, authority с revision+1 и неизменными остальными полями, enrollment из проверенных receipts, activating_envelope=null, recovery_from=null. Инструмент подписывает и проверяет полный candidate Replay:

# enroll-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "body_file":"enrollment-body.json","admin_key_file":"admin/private.pem"}
/secure/sekvyr-provision transition --work-dir /secure/provision \
  --input enroll-request.json --output enrollment-1

Доставьте transition.json через отдельно авторизованный mTLS POST /v2/logs/{log}/transitions (не record.json); server проверяет exact CAS. Сохраните commit receipt, новый chain и cursor. Не генерируйте заново transition после lost acknowledgment. После enrollment bootstrap output остается тем же по snapshot/ключам, но initialize chain/body обязаны закрепить новый post-enrollment cursor.

Установите reviewed chart с ha.enabled=true, ha.trial=true, ha.maintenance=true, replicas=0, fencer replicas >=2. managedObjects, bootstrapSubjects, SA/Lease/material pins и admission scope соответствуют подписанному enrollment; bootstrap subject только явный admin. Identity/trust уже immutable и проверены. Для initialize body используйте recovery.Body: operation=initialize, новый recovery_id, previous_bootstrap_generation=0, previous_state_secret_uid="", bootstrap_generation=1, exact current cursor/snapshot, реальные pins, нормализованный Binding.Identity, SHA-256 пустых state.json bytes, allow_rollout=false и expiry не более 24 часов вперед. Сам state.json пока отсутствует.

# initialize-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<POST_ENROLL_SEQUENCE>",
                             "record_hash":"<POST_ENROLL_RECORD_HASH>"}},
 "config_file":"bootstrap-1/installation.json",
 "receipts_file":"bootstrap-1/receipts.json","binding_file":"binding.json",

Ожидается CheckpointRecoveryComplete; до него нельзя выдавать установку за активную. Сначала подтвердите completed state, target UID/bytes и отсутствие старого pending intent, затем запустите приложение и reviewed Helm upgrade с ha.maintenance=false, replicas=2 и sync.enabled=true. Требуйте свежие условия/checkpoint и фактическое чтение приложением. Rollout остается OFF; --enable-rollout recovery не передается.

6.5. Дальнейшие публикации

Каждая snapshot-команда получает новую полную plaintext-конфигурацию и следующую snapshot sequence/previous hash; chain cursor относится ко всем journal records, поэтому это другой счетчик. Snapshot/wrap не являются commit. При ротации read/publisher epochs или restore нужен pending=true: canonical record не экспортируется, затем admin transition с тем же activating envelope проходит полный Replay и online CAS. Подробности — эксплуатация. Standalone wrap-only команды нет: snapshot создает wrapper вместе со следующим snapshot. Не создавайте лишний head, чтобы скрыть устаревшие status или потерянный ответ.
