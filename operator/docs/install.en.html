Installation and independent bootstrap

Release candidate documentation. Operator, chart and offline sekvyr-provision: 0.1.0-rc.2; matching backend: 1.1.0-rc.4. Replace <REVIEWED_VERSION> with the reviewed chart version and <REVIEWED_DIGEST> with the selected image digest (sha256: + 64 hex). Verify the separate provision binary checksum. Placeholders are not deployable. Published panel 1.0.3 does not support the new E2E2 API; agent 1.0.3 is unchanged. This does not announce publication or compatibility with the old backend.

1. Choose a profile and trust boundary

Defaults are sync.enabled=false, rollout.enabled=false, ha.enabled=false. Sync and rollout require separate opt-ins. Pod Ready is process readiness; verify current CR status and the consuming application separately.

2. Reserve the namespace, TLS identities and permissions

An installation operates in one trusted administrative namespace. Restrict Pod creation and changes to bootstrap, Store, CR, targets and ServiceAccounts: Pod/Secret access can expose keys and decrypted values. Non-HA sync needs namespaced Secret CREATE, which Kubernetes RBAC cannot restrict by resource name; runtime also checks allowlists and ownership. HA has no Secret CREATE. The operator needs no Secret list/watch/delete or Pod delete; Deployment get/patch appears only with rollout opt-in.

Before runtime starts, prepare the namespace and three distinct Opaque Secrets: immutable P256 identity, immutable trust, mutable state. HA trust is first reserved, then populated and made immutable using the section-6 ceremony while the operator is stopped. Retain UIDs from successful CREATE responses. Recreating a name changes its identity. Keep private keys, passwords, JWTs and trust contents out of Helm values: values enter release history. External SA/Lease require create=false and explicit known UIDs; there is no lookup/TOFU or Helm adoption.

The supplied sekvyr-provision signs artifacts of the existing protocol; no custom signer is required. File operations support Linux. Prepare an existing current-UID-owned mode-0700 directory /secure/provision. Inputs and nested directories are private, JSON file references are relative to it, and files are normally 0600. Symlinks, hardlinks, FIFOs, path escape and overwrite are rejected. Existing output, including partial output, requires review and is never adopted on retry.

# keygen-node.json (private 0600):
{"role":"node"}
/secure/sekvyr-provision version
/secure/sekvyr-provision keygen --work-dir /secure/provision \
  --input keygen-node.json --output node
# node/private.pem: P256 PKCS8; node/public.json: public fingerprint.
# public-node.json: {"role":"node","private_file":"node/private.pem"}
/secure/sekvyr-provision public --work-dir /secure/provision \
  --input public-node.json --output node-public-copy

For HA, independently run keygen once per role: admin, publisher, witness, fencer, read, with distinct request/output names. Ed25519 roles produce private.pem/public.json; read produces only read-key.bin (32 random bytes). Do not collect every role on a server: designated custodians run the commands and transfer only the required public/ciphertext artifacts. Never regenerate a node while restoring its existing identity. Keep private manifests, plaintext and CREATE receipts out of Git, shell history and Helm values. Plain/non-HA may also use keygen/public, but bootstrap/recovery below require HA.

The node fingerprint is p256-sha256: plus SHA-256 of the SEC1 uncompressed public point (65 bytes), not the PEM/SPKI hash. TLS origins are exact HTTPS origins without credentials/path/query/fragment. Custom CAs use immutable ConfigMaps pinned by UID and the installation algorithm's derSetSHA256, not a text PEM hash. Missing CA references use system roots. Admission TLS needs the DNS SAN service.namespace.svc; .svc.cluster.local alone is insufficient.

Allow only necessary DNS and paths: operator → Kubernetes API/panel; E2E2 → witness; HA operator/fencer/witness → gateway; gateway → storage; API server → admission. A cross-namespace peer ANDs namespaceSelector and podSelector within one peer; API/admission IP paths separately pin exact IPs/ports. The chart does not install NetworkPolicy. Test allowed and denied packets; port-forward or YAML presence is not CNI isolation evidence.

3. Plain bootstrap

Register independently obtained issuer, audience sekvyr and public JWKS with the panel. Grant the namespace + SA-name machine only the intended environment/path. Panel authentication uses offline JWKS, not TokenReview. Runtime SA UID pins are a separate check; Pod deletion does not immediately revoke a JWT. An E2E project is rejected in Plain mode.

A pure Plain immutable trust Secret contains the strict JSON below. This bundle is not automatically signed: trust comes from independent provisioning, authorized origins and the exact immutable Secret UID.

{
  "schemaVersion": 1,
  "protocol": "plain-v1",
  "installationID": "<INSTALLATION_UUID>",
  "bootstrapGeneration": 1,
  "namespace": "secret-sync",
  "serviceAccount": "operator-reader",
  "panelOrigin": "https://panel.example.invalid",
  "nodePublicKeyFingerprint": "p256-sha256:<PUBLIC_POINT_SHA256>"
}

The mutable state Secret's installation.json contains only installationID and bootstrapGeneration. A new non-HA installation also requires state.json:

{"version":1,"installationID":"<INSTALLATION_UUID>","bootstrapGeneration":1,
 "trustBundleUID":"<TRUST_SECRET_UID>",
 "nodeFingerprint":"p256-sha256:<PUBLIC_POINT_SHA256>","bindings":{}}

This empty state is not a recovery mechanism for an existing installation. HA initialize instead begins with no state.json key; reviewed signed recovery creates it as described below.

5. Independent E2E2 bootstrap and read wraps

  1. A trusted publisher holds an AES read key separately from its Ed25519 signing key. The operator receives only the read key inside a signed encrypted wrap for its P256 node. Neither a project password nor a publisher private key is sent to the panel/operator. Anyone holding a shared writer password can cryptographically sign; a UI role cannot remove that ability.
  2. Independently verify publisher/witness/admin public keys and fingerprints, realm/project/environment/view/log scope, genesis hash and a positive minimum checkpoint. Do not bootstrap trust from the same potentially hostile panel. Publisher JavaScript is itself a trust boundary.
  3. Provision strict schemaVersion 2 trust using the actual wire: installation/node pins and viewTrust bound to Store UID + binding ID. The public design example is not deployable: description/exampleOnly and placeholders fail strict parsing.
  4. Create a view in the unreleased panel; stage a publisher-signed complete encrypted snapshot, not an individual key patch. After canonical commit and fresh witness proof, index its hash. The owner grants the signed wrap to the specific machine; whole-environment/path permission and explicit view grant are both required. /api/e2e2/views, /envelopes, /index, /readers are not advertised as panel-1.0.3 APIs.
  5. For a separate new E2E2 binding use {mode: E2E, protocol: e2e2, trustKey: runtime-view, freshness: {mode: WitnessCurrent}} plus source.viewId. Existing binding encryption/trust references are immutable: this is not a patch of the preceding Plain binding. Allow exact panel/witness origins and CAs. There is no E2E1/offline/polling fallback.

Use sekvyr-provision: command contract and exact JSON request types. keygen/public prepare keys; genesis/snapshot/transition produce signed offline artifacts. bootstrap/recovery currently require HA E2E2 config: they are not a Plain/non-HA installer or lost-state restore tool. Non-HA uses its strict trust/state wire and a separately reviewed administrative installation. Harness keys/vectors remain public fixtures; no ready-made bootstrap UI is promised.

6. HA trial: offline genesis to the first sync

An installation supports one log/view. This sequence creates generation 1; it does not restore lost state. Provision commands perform no network, Kubernetes or storage commits. Prepare every private request file and nested protocol body before running it, replacing reviewed placeholders. Every request field is required, including pending and empty state_file; explicit nullable protocol unions remain null. Duplicate/unknown fields and case aliases are rejected.

6.1. Genesis and independent pin

Prepare genesis-body.json using journal.GenesisBody / Authority: format=sekvyr-journal-genesis-v1, exact five-UUID scope, panel_origin, initial authority revision/epochs, separate public admin/publisher/witness/fencer keys and recovery_from=null for a new log. journal.Key contains only key_id/public_key, not the entire provision descriptor. An independent administrator signs genesis.

# genesis-request.json
{"body_file":"genesis-body.json","admin_key_file":"admin/private.pem",
 "admin_public_file":"admin/public.json"}
/secure/sekvyr-provision genesis --work-dir /secure/provision \
  --input genesis-request.json --output genesis

Outputs are record.json, records.json and registration.json. Genesis passes Sign → Replay. Independently verify the original admin public key, log ID, genesis hash and minimum cursor; preserve reviewed-registration.json separately from the server. A new log may pin genesis sequence 0, but runtime trust requires a positive snapshot. Raise floors only using separately verified receipts, never lower them based on panel responses.

Separately provision reviewed gateway/storage and witnesses with TLS/mTLS and distinct service identities. The operator receives no upstream S3 credential or admin key. Actual initialization CLI:

/secure/sekvyr-witness canonical-init \
  --config /secure/canonical-witness.json \
  --registration /secure/provision/genesis/record.json \
  --allow-trial-canonical-ledger

This is an online administrative command, separate from offline provision. Retain its CAS receipt and the full signed chain from genesis. Resolve a lost response against that CAS before trying anything else. Each later command takes independently reviewed registration, a bounded complete Record array and the exact expected final cursor:

"chain": {
  "registration_file": "reviewed-registration.json",
  "records_file": "reviewed-complete-records.json",
  "expected_cursor": {"journal_sequence":"<DECIMAL_SEQUENCE>",
                      "record_hash":"<EXACT_RECORD_HASH>"}
}

Do not substitute CurrentState JSON for signed records. Provision checks signatures, continuity, the positional floor hash and exact final cursor. It cannot know a newer live head exists; online CAS/floor gates remain mandatory.

6.2. First full snapshot and reader wrap

Register the view and machine permissions in the matching backend. The trusted publisher prepares Header and Plaintext: the same scope, initial sequence=1, previous_hash=64 zeros, action=initial, intent=publish, protocol=e2e2, suite=HKDF-SHA256+A256GCM+Ed25519, current epochs/key ID, exact entry_count, parents=[] and restored_from=null. Set input snapshot_salt to an empty string: SealSnapshot generates random salt/nonce. Values use full JSON Plaintext with format=sekvyr-e2e2-values-v1, context and sorted path/name/value entries, never executable .env or an individual key patch.

# snapshot-request.json
{"pending":false,
 "chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "header_file":"header.json","plaintext_file":"values.json",
 "read_key_file":"read/read-key.bin",
 "publisher_key_file":"publisher/private.pem",
 "publisher_public_file":"publisher/public.json",
 "recipient_public_file":"node/public.json"}
/secure/sekvyr-provision snapshot --work-dir /secure/provision \
  --input snapshot-request.json --output snapshot-1

Outputs are envelope.json, reader-wrap.json, candidate.json and, for current epochs, record.json. Signature, Decrypt and exact plaintext equality are checked before writing. The wrap encrypts AES for the explicitly selected node public key; neither node/signing private keys nor plaintext go to the panel. candidate committed=false denotes offline preparation, not a commit or its proof.

Separately stage the envelope in the panel API, perform canonical witness commit at the exact cursor, obtain a fresh witness proof/index and grant the signed wrap to the specific machine through readers. Verify the committed hash/sequence and export the complete signed chain. A first positive canonical snapshot must exist before bootstrap; a genesis-only checkpoint fails runtime trust parsing. HA uses the canonical journal profile, not the development filesystem ledger.

6.3. UID receipts, reservation and unsigned bootstrap

Stop the operator: replicas=0/maintenance. An administrator creates the namespace, distinct SAs, Lease, Store/CR, reserved target and Deployment; the application remains at replicas=0. Retain actual CREATE UIDs and current resourceVersions. The node Secret can be immutable immediately using the prepared private.pem. Trust requires a reservation/seal ceremony: first CREATE a mutable Opaque reservation and retain its real UID; this is not runtime trust yet. State stays mutable with its marker and no state.json. Never invent a trust UID, use lookup/TOFU or start the operator with a reservation.

Prepare installation.Config with HA config, CA/Secret pins and real UIDs. Put one actual Store binding in binding.json using its Go JSON form. If target explicitly sets allowEmpty: false, omit that default only from the CLI copy. Preserve an explicit true. uid-receipts.json has exactly {"enrollment": <journal.Enrollment>, "binding": <recovery.Binding>}. Enrollment includes the full canonical-sorted AllowedObjects set, distinct SAs/UIDs and Lease ref. Binding includes Store/CR names/UIDs/generations, binding/view/target and Identity. Only bootstrap accepts explicit empty Identity and derives the existing Go JSON BindingIdentity. This is neither JCS nor a signature.

# bootstrap-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "config_file":"ha-installation-input.json","receipts_file":"uid-receipts.json",
 "binding_file":"binding.json","node_public_file":"node/public.json",
 "trust_key":"runtime-view","publisher_key_id":"<PUBLISHER_KEY_ID>"}
/secure/sekvyr-provision bootstrap --work-dir /secure/provision \
  --input bootstrap-request.json --output bootstrap-1

installation.json, trust.json, state-marker.json and normalized receipts.json are unsigned administrative materials. In one exact UID/resourceVersion CAS the administrator populates trust.json bytes and sets immutable=true on the reserved trust Secret. Independently reread UID, immutable, type and exact bytes, and verify node/state/CA refs. Never overwrite an immutable Secret. UID/RV mismatch stops the procedure; a new bootstrap requires a separate administrative procedure. Helm receives refs, not payloads/keys.

6.4. Signed enrollment, then exact-cursor initialize

The independent admin prepares TransitionBody: kind=enroll-installation, current scope/genesis/expected cursor/previous_authority_digest, authority with revision+1 and all other fields unchanged, enrollment from reviewed receipts, activating_envelope=null and recovery_from=null. Provision signs and checks full candidate Replay:

# enroll-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<DECIMAL_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "body_file":"enrollment-body.json","admin_key_file":"admin/private.pem"}
/secure/sekvyr-provision transition --work-dir /secure/provision \
  --input enroll-request.json --output enrollment-1

Submit transition.json through separately authorized mTLS POST /v2/logs/{log}/transitions, not record.json; the server checks exact CAS. Retain the commit receipt, new chain and cursor. Do not regenerate a transition after lost acknowledgement. Snapshot/key-derived bootstrap output stays the same, but initialize chain/body must pin the new post-enrollment cursor.

Install the reviewed chart with ha.enabled=true, ha.trial=true, ha.maintenance=true, replicas=0 and fencer replicas >=2. managedObjects, bootstrapSubjects, SA/Lease/material pins and admission scope match signed enrollment; bootstrap subject is an explicit administrator only. Identity/trust are already immutable and verified. The initialize recovery.Body contains operation=initialize, a new recovery_id, previous_bootstrap_generation=0, previous_state_secret_uid="", bootstrap_generation=1, exact current cursor/snapshot, real pins, normalized Binding.Identity, SHA-256 of empty state.json bytes, allow_rollout=false and expiry at most 24 hours ahead. state.json is still absent.

# initialize-request.json
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-complete-records.json",
          "expected_cursor":{"journal_sequence":"<POST_ENROLL_SEQUENCE>",
                             "record_hash":"<POST_ENROLL_RECORD_HASH>"}},
 "config_file":"bootstrap-1/installation.json",
 "receipts_file":"bootstrap-1/receipts.json","binding_file":"binding.json",

 "admin_key_file":"admin/private.pem"}
/secure/sekvyr-provision recovery --work-dir /secure/provision \
  --input initialize-request.json --output initialize-1

export KUBECONFIG=/secure/admin.kubeconfig
/secure/sekvyr-checkpoint-recovery \
  --installation-file=/secure/provision/bootstrap-1/installation.json \
  --plan=/secure/provision/initialize-1/plan.json \
  --envelope=/secure/provision/snapshot-1/envelope.json \
  --reader-wrap=/secure/provision/snapshot-1/reader-wrap.json \
  --allow-trial-canonical-ledger

Provision performs Sign → recovery.Verify against verified offline records. Native checkpoint-recovery separately verifies current online journal/witness and real Kubernetes refs. Expect CheckpointRecoveryComplete; do not declare the installation active beforehand. Verify completed state, target UID/bytes and absence of historical pending intent, then start the application and perform reviewed Helm upgrade to ha.maintenance=false, replicas=2, sync.enabled=true. Require fresh conditions/checkpoint and actual application reads. Rollout remains OFF; omit recovery --enable-rollout.

6.5. Subsequent publication

Each snapshot command takes a new complete plaintext configuration and next snapshot sequence/previous hash; journal cursor counts all record kinds and is a separate counter. Snapshot/wrap are not a commit. Read/publisher epoch rotation or restore requires pending=true: no canonical record is exported, and an admin transition with that same activating envelope must pass full Replay and online CAS. See operations. There is no standalone wrap-only command: snapshot creates a wrap with the next snapshot. Never create an unnecessary head to conceal stale status or a lost response.

Coverage, not a compatibility promise

Stage 7 exercised Linux amd64: Kubernetes v1.34.1+k0s with 960d…, kind v1.37.0 with diagnostic d328…. Final d328/readiness timeout=10 was not rerun on 1.34. ARM64, new RCs, other minors/storage engines require their own tests. The tested backend digest 3e25… is unreleased; unchanged published agent 1.0.3 was tested only as a Plain init/sidecar regression. Full hashes and retained incomplete attempts are in evidence.

Stage-7 cleanup preserved foreign Docker resources, but strict global network audit was FAIL: empty IPv6 raw chains / 3 nft objects / a kernel anycast route remained. The user explicitly accepted this residue; original sysctls were not recorded, so exact host restoration is not claimed. Before another Docker/kind trial, independently capture sysctls, IPv6 address flags/anycast, firewall/routes and complete image inventory. Do not repeat on a shared host without a separate cleanup plan. WSL clock backsteps were observed without identifying their source; time guards were not weakened.
