Operations and controlled recovery

Operator/chart/provision 0.1.0-rc.2 and matching backend 1.1.0-rc.4 documentation. Substitute reviewed versions/digests/checksums; new RCs do not inherit an old digest's live coverage. Published panel 1.0.3 has no E2E2 API; agent 1.0.3 is unchanged. Offline sekvyr-provision bootstrap/recovery and native checkpoint-recovery currently require HA E2E2. Installation provides the full reservation/seal sequence; no custom signer is required.

1. Verify data separately from Pod Ready

kubectl get sekvyrsecret application-runtime -n secret-sync \
  -o jsonpath='{.status}'
kubectl get sekvyrstore application-secrets -n secret-sync \
  -o jsonpath='{.metadata.uid}{" "}{.metadata.generation}{"\n"}'

Match current CR generation, Store UID/generation, a new attempt timestamp and lastAttemptTime == lastSuccessfulSyncTime. E2E2 needs current Ready/BootstrapReady/WitnessReady/DataCurrent/RolloutReady and the exact verified checkpoint; Plain uses WitnessReady Unknown/NotApplicablePlain without a checkpoint. A wait on an old True condition does not prove post-upgrade or post-fault synchronization. Privately verify values inside the application without putting canaries or their digests in logs/Events/reports.

Compare those timestamps on SekvyrSecret. The aggregate SekvyrStore status reports the oldest successful sync among its bindings; aggregating the same child statuses again does not advance that timestamp.

Operator /healthz and /readyz are process probes. Fencer /readyz performs a fresh online journal check; /healthz is process-only. Default fencer readiness timeout is 10 seconds, configurable 1..30; this does not authorize cached trust or failure bypass. Do not fix clock backsteps/future Leases by relaxing time guards or clearing state.

Sealed panel, timeouts, API denial, 401/403 and cryptographic failures preserve the last good Secret/application and report failure. This preserves already-issued data, not immediate revocation. A pending rollout needs a new successful source verification. StateMissing/StateReplaced, RecoveryPending and TargetMissing/TargetReplaced require review; do not delete state/pins to force a restart.

2. Rollout has three explicit authorization layers

  1. Complete administrative values: sync.enabled=true, rollout.enabled=true, nonempty exact rollout.allowedDeployments.
  2. The selected Store binding's exact rollout.allowedDeployments, within the installation allowlist.
  3. SekvyrSecret spec.rollout.enabled=true with explicit requested deployments allowed by that binding. Deployments must already exist, have known UIDs and consume the selected Secret.
# Fragments from separate documents, not a single values file:
# Helm values:
sync: {enabled: true}
rollout: {enabled: true, allowedDeployments: [sample-api]}
# Store binding:
rollout: {allowedDeployments: [sample-api]}
# SekvyrSecret.spec:
rollout: {enabled: true, deployments: [sample-api]}

Use reviewed native Helm upgrade for values, and owner UID/resourceVersion checks for Store/CR changes. No wildcard or selector broadening. Initial creation, equal plaintext and enabling opt-in cause no historical restart. A real change persists an opaque revision and durable intent; Debouncing waits, DeploymentPaused retains pending work. Only the owned Pod-template annotation secrets.sekvyr.ru/restart-<targetSecretUID> changes through UID/RV CAS. Recreated Deployments are not silently adopted.

Secret volumes can update without restart when applications read a consistent kubelet projection without subPath. EnvFrom does not change a running process. Coordinate external reloaders separately: the trial opted out only its own Deployments with reloader.stakater.com/auto, secret.reloader.stakater.com/auto, configmap.reloader.stakater.com/auto set to "false". No global controller was changed. Exactly-once restart with other writers is not promised.

3. Backup inventory

MaterialHandling
Node identity, trust, marker/state.json, UIDs, installation/Helm values, CRDs/CRsEncrypted, access-controlled copies. Retain generation, scope, genesis/cursor, CREATE receipts and Store/CR/binding/target UID relationships. Old state YAML alone proves no freshness.
Publisher AES/signing keys and independent admin keyHeld by trusted owners separately from panel/operator backup. Lost private material cannot be reconstructed by issuing a new manifest.
Witness/fencer keys, TLS/mTLS, CAs, gateway policiesSeparate roles and check authorized public keys/epochs. The operator receives neither upstream S3 credentials nor the admin signing key.
Panel and canonical journalSeparate restore boundaries. Preserve the entire signed chain, object versions, COMPLIANCE receipts/retention and independently pinned minimum cursor. Do not delete versions or rewrite the journal to match an old panel.

Coordinate a window: stop administrative publications/rotations, verify current state, then capture related receipts. Raw Kubernetes exports belong only in a mode-0700 private directory under umask 077 and an encrypted backup. Do not print Secret YAML in a terminal/ticket/CI; base64 is not encryption. Target Secrets contain plaintext and need the same protection.

Test restoration separately. Trial SeaweedFS retention/fsync does not prove independent production fault domains, WORM against root, or power-loss durability. Replicas or an untested backup do not establish those properties.

4. Restore does not reset a checkpoint

A restored panel may lag the independent journal. E2E2 must not trust its old index as current: missing current ciphertext fails closed, without offline fallback. Recover encrypted artifacts by their known hashes; do not reinitialize genesis or lower floors. Recreating a Kubernetes name gives a new UID, so old pins cannot be repaired by applying old YAML.

HA state loss / node replacement: stop all old operator writers. Trial chart uses ha.maintenance=true, replicas=0; keep fencer replicas >=2. Wait for physical old-Pod absence, not just Deployment Ready. Retain old generation/state UID and last verified target. Precreate new immutable identity/trust and a new mutable state with new names/UIDs; its marker uses a higher bootstrap generation. Never adopt a foreign target UID.

  1. An independent administrator signs enrollment/reconfiguration under current authority and exact namespace/SA/Lease/material/object UIDs. Old grants become inactive; a new grant activates only after every object barrier.
  2. Prepare new strict trust, current envelope/wrap and a signed operation=recover plan. It binds exact cursor/snapshot, previous generation/state UID, higher generation/new state UID, node/trust pins, Store/CR generations, target UID and the expected raw state.json hash.
  3. The plan must be unexpired and at most 24 hours ahead. Sign with the currently authorized independent admin key, never embedded private material. A new marker/plan is not a substitute for a valid signature.

Prepare the plan using the supplied offline CLI

Use RecoveryRequest and the provision contract. First repeat bootstrap for the higher generation: real CREATE UIDs, trust reservation → exact UID/RV populate+immutable → independent reread, with the operator still at 0. Copy the exact normalized Identity from bootstrap output into reviewed Binding receipts and recovery.Body; recovery never derives it. Sign and online-commit the new enrollment, then pin its post-enrollment chain/cursor for the plan. Do not mix an older body cursor with a newer chain.

# recover-request.json (private 0600):
{"chain":{"registration_file":"reviewed-registration.json",
          "records_file":"reviewed-post-enrollment-records.json",
          "expected_cursor":{"journal_sequence":"<EXACT_SEQUENCE>",
                             "record_hash":"<EXACT_RECORD_HASH>"}},
 "config_file":"bootstrap-next/installation.json",
 "receipts_file":"bootstrap-next/receipts.json","binding_file":"binding.json",
 "body_file":"recover-body.json","state_file":"reviewed-state-bytes.bin",
 "admin_key_file":"admin/private.pem"}
/secure/sekvyr-provision recovery --work-dir /secure/provision \
  --input recover-request.json --output recovery-next

reviewed-state-bytes.bin contains exact state.json bytes expected in the new pinned state Secret, without JSON normalization. If that data key is absent, retain an explicit empty 0600 file: operation=recover requires state_file. initialize uses state_file="" and SHA-256 of empty bytes. A separate recovery.Body binds previous generation/old state UID, new material UIDs, current snapshot/cursor, expiry and allow_rollout=false. Provision signs with the current admin and calls recovery.Verify. For the online CLI below, use /secure/provision/recovery-next/plan.json as --plan and bootstrap-next/installation.json as --installation-file. These outputs are not commit receipts and never bypass online journal/witness checks.

export KUBECONFIG=/secure/admin.kubeconfig
/secure/sekvyr-checkpoint-recovery \
  --installation-file=/secure/provision/bootstrap-next/installation.json \
  --plan=/secure/provision/recovery-next/plan.json \
  --envelope=/secure/provision/current-envelope.json \
  --reader-wrap=/secure/provision/current-reader-wrap.json \
  --allow-trial-canonical-ledger

CLI transport uses encrypted offline exports, but journal and witness remain online. Rollout defaults off. Changed-data recovery additionally requires explicit CLI --enable-rollout, matching installation policy and signed allow_rollout=true. Equal-data recovery creates no historical restart.

Prepared is persisted before target update, followed by complete. Resolve a lost acknowledgement against the same plan/recovery ID and observed phase; do not generate a new ID or automatically rebase to the latest cursor. Exact-plan continuation is verified; concurrent journal advancement may leave RecoveryPending and require a newly reviewed plan. There is no atomic journal/Kubernetes transaction: a lagging check does not authorize lowering an already newer applied target.

Continue only with retained UIDs/context and verified integrity. After CheckpointRecoveryComplete, verify current state/target, exit maintenance, restore two operator replicas and require fresh sync. Never transfer old pending intent into a new generation. Retain previous state names/UIDs in ha.webhook.retiredStateSecrets until explicit administrative cleanup; do not narrow admission scope halfway through recovery.

The CLI requires HA E2E2 and is not a Plain/non-HA lost-state restore command. Those profiles have no automatic lost-high-water-state repair: stop writers, preserve the target, review restoration of the original object/backup or a separate migration using a new target/bootstrap. Never clear bindings, remove UID pins or adopt foreign Secrets to hide state loss.

Offline rotation preparation

keygen creates one new role per call. For AES use role=read with a new output; incrementing the epoch while reusing AES does not revoke the old node. snapshot with pending=true prepares the next full envelope/wrap without record.json; transition then signs the existing TransitionBody with activating_envelope and checks candidate Replay. rotate-read-key requires action=rotate-read-key and the next read epoch; rotate-publisher uses action=update, next policy epoch and new publisher public keys. Restore uses kind=recover with checked history/recovery_from, never a sequence decrease. Rotate-admin/witness/fencer use their closed kind and current admin, without an unnecessary activating snapshot.

/secure/sekvyr-provision snapshot --work-dir /secure/provision \
  --input reviewed-pending-snapshot.json --output pending-rotation
/secure/sekvyr-provision transition --work-dir /secure/provision \
  --input reviewed-transition-request.json --output signed-rotation

Requests have the same mandatory fields shown in installation; transition requests reference a separate exact BodyFile. Pending artifacts are not published current state. Online CAS, coordinated signer/pin changes and independent receipts remain mandatory. There is no wrap-only command: node rotation using this CLI prepares a fresh AES/read epoch and next full snapshot/wrap for the new node, followed by admin transition/enrollment and signed recovery. No custom signer is needed. Other authorized readers also need verified wraps; this tool does not manage online grants. Retain exact ciphertext/plan output for lost-ack resolution: rerunning snapshot generates new salts/nonces and a different hash.

6. Upgrade and constrained rollback

  1. Select a reviewed chart version/image digest and check backend/protocol/state compatibility. Save manifests, CRD schemas, complete values, external UID receipts, cursor and backup. Exclude concurrent administrative writers.
  2. Review CRD schema changes separately. Helm upgrade does not automatically upgrade crds/. An administrator separately applies reviewed additive schema preserving existing CRs, after checking pruning, validation and stored versions.
  3. Render complete new values; compare RBAC, webhook, material refs and Pod templates. Reuse-values is not a review. Current resources are shared by operator/fencer: a memory change can replace both pairs.
CHART='/secure/sekvyr-operator-<REVIEWED_VERSION>.tgz'
helm template secret-sync "$CHART" --namespace secret-sync \
  -f /secure/next-values.yaml > /secure/next-render.yaml
helm upgrade secret-sync "$CHART" --namespace secret-sync \
  -f /secure/next-values.yaml --skip-crds --wait --timeout 180s

After Ready, wait for old changed-Pod UIDs to be physically absent. Capture UTC cutover/previous lastSuccess and require a new successful attempt after cutover with current CR/Store UID/generation/checkpoint, then verify the application. Do not publish another head merely to mask stale status.

Helm rollback restores manifests, not journal, CRDs, keys or data. helm rollback secret-sync <REVIEWED_HELM_REVISION> --namespace secret-sync --wait --timeout 180s is conditional on old binaries understanding current CRD/state/authority and preserving present pins/floors. After a higher bootstrap generation or incompatible wire, automatic rollback is unsupported: use a forward fix or independently signed migration. Check retained ConfigMap UID and exact bytes; never adopt by name.

CRD rollback is not part of Helm rollback. An older schema can prune fields, reject current CRs or misunderstand stored versions. Do not delete CRDs to downgrade: deletion removes their CRs across namespaces, potentially GC-deleting targets using Delete policy. No safe downgrade is claimed without independently tested schema/data migration.

7. Uninstall and data retention

Choose deletionPolicy: Retain when creating a binding; the policy is immutable. Existing Delete needs a separate data-preservation/migration plan, not an ad-hoc policy patch or ownerReference removal. The chart does not own target/identity/trust/state Secrets or external SA/Lease. Deleting a Delete CR may GC its target despite no operator Secret DELETE permission. Deleting the namespace also deletes Retain data.

  1. Stop publications and disable requested rollout/suspend under the reviewed plan. HA: maintenance=true/replicas=0, physical old-operator-Pod absence; do not disable fencer/admission while writers remain. Non-HA: first set both sync.enabled=false and rollout.enabled=false in complete reviewed values, then wait for old sync-enabled Pods to disappear.
  2. Verify current target UID/data/application and backup. Uninstall only the captured release, not a shared namespace/CRD.
helm uninstall secret-sync --namespace secret-sync --wait --timeout 180s

Verify only owned Deployment/Role/RoleBinding/HA cluster resources disappeared and external pins/targets survived. configuration.retain=true keeps immutable ConfigMap revisions: after all consumers are absent, delete only reviewed objects with DeleteOptions UID preconditions. Keep does not authorize adoption or trust rollback. CRDs, Store/CR and keys need a separate lifecycle accounting for other installations.

Check own forward/helper processes and temporary credentials are gone; compare independent foreign workloads/volumes/networks/host baseline. No global prune. Stage 7 passed strict Docker resource comparison but accepted an explicit global IPv6 exception, not exact whole-host restoration. Capture initial sysctls, IPv6 anycast/address flags, firewall/routes and full image inventory before a new trial.

Coverage and limits

Actual Linux amd64 coverage: 960d on Kubernetes 1.34.1+k0s, d328 on kind 1.37.0; final d328/timeout-10 was not rerun on 1.34. ARM64 and new RCs have no inherited coverage. Stage-7 backend 3e25 had 9 open HIGH OS CVEs / 45 matches without exploitability proof or waiver; a fix needs fresh scan/acceptance.

No production WORM/independent fault-domain, cross-object/system atomic freshness, exactly-once restart or Byzantine/root/control-plane/storage / surviving-request etcd-RV-rewind guarantees. For E2E2, plaintext read keys, project passwords and private publisher keys stay out of the panel. Trusted publisher/browser JavaScript and Kubernetes plaintext access remain trust boundaries.
