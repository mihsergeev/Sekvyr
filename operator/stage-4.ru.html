Sekvyr operator: результат этапа 4

Реализована цепочка API панели → независимый witness → проверка E2E2 → долговечный checkpoint → Kubernetes Secret. Синхронизация включается явно: sync.enabled=true. По умолчанию она выключена.

Этап 4 проверен на реальном тестовом Kubernetes. Все 15 сценариев живого E2E прошли. Этап 5 не начат. Перезапуск приложений оператором, выпуск, публикация и production rollout не выполнялись. Дальнейшая работа требует решения пользователя.

Что реализовано

КомпонентПоведение
API панели и миграция 0028Стабильные UUID realm/project/environment/view/log, неизменяемые envelope по hash, явные reader grants и подписанные обертки ключа. Машинное чтение требует действующей личности и полного права на окружение. Панель не получает E2E2 read key или закрытый ключ publisher.
ПубликацияДоверенный publisher подписывает и размещает полный ciphertext. Witness отдельно проверяет подпись, область, эпохи, предыдущий hash и точный CAS. Индекс панели обновляется только после свежего подписанного witness proof и остается производным указателем.
Сервис witnessОтдельный HTTPS-процесс, отдельный ключ и том. Offline genesis подписывает независимый администратор; runtime закрепляет его hash и ключ. Полный replay журнала, межпроцессная блокировка, исключающее создание записи и fsync до ответа. Сетевого reset/register/delete API нет.
ТранспортТочные разрешенные HTTPS origins, UID и DER pins доверенных CA, запрет redirect и прокси из окружения, ограничения времени и размера. Вход по projected ServiceAccount JWT; публичный ключ ноды отправляется отдельно от значений.
CheckpointПредварительно созданный Secret с закрепленным UID. State связан с installation ID, bootstrap generation, trust bundle UID, ключом ноды, Store/binding/CR/target UID. Принятый high-watermark сохраняется через resourceVersion CAS до изменения целевого Secret.
Целевой SecretТолько разрешенные имена в одном namespace. Чужие объекты не принимаются по labels или revision. Полный снимок проверяется до выбора ключей. Данные, непрозрачная случайная revision, checkpoint и неактивный rollout intent записываются вместе.
Повторная синхронизацияРавные фактические данные сохраняют revision; новый canonical ciphertext может продвинуть checkpoint без перезагрузки приложения. Отказ чтения или проверки не меняет Secret. Ошибка записи target не откатывает уже сохраненный checkpoint; неоднозначный результат требует повторной сверки или административного восстановления. DataCurrent становится false, история последнего успешного применения сохраняется.
Статус и RBACСтатус ребенка закрепляет наблюденные UID/generation Store. Успех от старой конфигурации, suspended или deleting CR не считается текущим. DataCurrent отделен от готовности rollout. Нет прав list/watch/patch/delete для Secret и нет прав менять приложения.

Первый тестовый запуск обнаружил ошибку harness: возвращенный инициализацией ключ распечатывания панели не сохранялся для рестарта. Ошибка исправлена, повторный полный прогон выполнен с чистой установкой и новым журналом. Требование распечатывания панели сохранено; восстановление после ее отключения прошло через штатный TLS API.

Пройденные сценарии живой приемки

  • Первый подписанный снимок доходит до настоящего Secret и читается приложением.
  • Обновление значений подхватывается приложением с прежними boot ID и PID. Canary читает пару файлов через один разрешенный каталог AtomicWriter ..data.
  • Новый ciphertext с тем же plaintext продвигает checkpoint, сохраняя revision и счетчик reload.
  • Подмена подписи, ciphertext, старый envelope и fork отклоняются; предыдущие принятые данные сохраняются. Устаревший индекс панели не выбирает head.
  • Остановка панели и witness помечает данные как нетекущие, сохраняя последний Secret. После восстановления проверяется свежий canonical head.
  • Рестарт оператора сохраняет ключ ноды и checkpoint. Потеря или замена state с прежним именем не приводит к новому автоматическому bootstrap.
  • Чужой Secret остается неизменным. Проверяются фактические запреты RBAC, отсутствие секретов в логах и публичном CR status.

Границы результата

Это еще не production readiness. Реализован явный профиль development-filesystem-not-worm, требующий --allow-development-filesystem-ledger. Обычная файловая система не защищает журнал от привилегированного удаления или физического отката. Для production требуется отдельно проверенная независимость неизменяемого журнала и его restore-domain.

  • Тестовое приложение само умеет перечитывать Secret volume. Произвольное приложение должно поддерживать такой reload; переменные окружения уже работающего процесса от обновления Secret не изменяются.
  • Оператор не перезапускает Deployment. Rollout intent имеет eligible=false; опциональный перезапуск относится к этапу 5.
  • HA fencing, ротации ключей/полномочий и полные процедуры восстановления остаются для этапа 6. Текущий сервис отклоняет неподдерживаемые переходы полномочий.
  • Транзакции между CR, Store, state и target нет. Повторная проверка полномочий уменьшает окно гонки, но не обещает мгновенный отзыв уже выполняющейся записи.
  • Потеря state и неоднозначный crash после создания target требуют явного административного восстановления. Оператор не восстанавливает доверие из labels или annotations.
  • Панель после рестарта может требовать штатного распечатывания. Последние значения в уже работающем приложении при этом сохраняются.
  • Проверен один тестовый Kubernetes 1.34.1. Остальные Kubernetes/storage комбинации этим прогоном не подтверждены.
  • Синхронизация этого этапа реализована для E2E2. Plain/E2E1 runtime оператора, интерфейс управления publisher/grants, миграции существующих проектов и UI совместимости не входят в результат. Legacy emergency export явно отказывает при наличии E2E2 views.
  • Успешный reconcile не стирает старые значения из памяти приложения и не предотвращает показ старого уже существующего Secret при административном restore etcd. Для строгой свежести при старте потребуется отдельный admission/app gate.
  • Совместный откат всех независимых корней доверия и журнала невозможно обнаружить этим протоколом. Независимый trusted publisher также обязателен: вредоносный код интерфейса панели не должен получать разблокированные publisher keys.

Окружение после тестов

Ресурсы обоих удаленных тестовых запусков убраны: восемь namespace, два тестовых CRD и связанные persistent volumes отсутствуют. Независимая проверка подтвердила Ready всех нод и штатных workloads. Временные port-forward и отдельный процесс сборки остановлены; сгенерированные ключи, пароли и копии административного kubeconfig удалены из обоих каталогов тестов.

Локальный kind от первой попытки пока недоступен: WSL не отвечает даже на отдельный короткий probe. Общая перезагрузка WSL и очистка чужих ресурсов не выполнялись. Этот локальный остаток не использовался как доказательство успешного E2E.

Контракт и исходники

После обновления canary: один reload, ноль ошибок чтения конфигурации и ноль рестартов контейнера; durable checkpoint достиг sequence 3. После намеренной замены state итоговые Ready/DataCurrent стали false — это ожидаемое завершение отрицательного теста.
