Sekvyr operator: результат этапа 5

Реализован опциональный перезапуск Deployment после проверенного E2E2-изменения данных Kubernetes Secret. Одинаковые выбранные значения сохраняют revision и не создают новый запрос на перезапуск. Первое создание Secret и последующее включение rollout также не создают исторического restart.

Этап 5 прошел приемку: 20/20 живых E2E на реальном Kubernetes. Этап 6 не начат. Публикация и production rollout не выполнялись. Дальнейшая работа требует решения пользователя.

Как включается

Нужны три независимых разрешения: установка оператора, административный binding Store и явный запрос SekvyrSecret. Все Deployment находятся в одном namespace и должны реально использовать целевой Secret. По умолчанию rollout выключен.

sync:
  enabled: true
rollout:
  enabled: true
  allowedDeployments: [application]

# В нужном binding Store:
rollout:
  allowedDeployments: [application]

# В spec нужного SekvyrSecret:
rollout:
  enabled: true
  deployments: [application]

Helm передает отдельный --enable-rollout, который должен совпадать с административной конфигурацией и требует включенного sync. RBAC разрешает только get,patch конкретных Deployment. Прав на scale, удаление Pod, Deployment update/list/watch нет.

Что предотвращает лишние перезапуски

СценарийПоведение
Первое создание, включение rolloutНе создают eligibility. Приложение запускается обычным способом с уже созданным Secret.
Одинаковые значенияСравниваются фактические выбранные bytes после полной E2E2-проверки. Новый ciphertext или checkpoint без изменения данных не меняет непрозрачную revision и не создает новый rollout.
Настоящее изменениеНовая случайная revision и intent записываются вместе с данными Secret. Разрешение на этот intent предварительно сохраняется в защищенном state.
Частые измененияDebounce одного binding: 5 секунд тишины, не более 30 секунд от первого незавершенного разрешенного изменения. Время сохраняется при рестарте оператора.
Сбой панели или witnessНовый или отложенный rollout не выполняется. Возобновление требует свежей проверки canonical head, полного снимка и текущих полномочий. Старый успешный результат из памяти не используется.
Повторная обработка, потерянный ответСверяются текущая annotation и долговечная отметка выполнения для revision/Deployment UID. Уже примененный intent не патчится заново из-за исчезнувшей annotation.
Paused, denied, timeoutSecret может быть текущим при RolloutReady=false. Старый failed status допускает одну попытку с новой revision, которая может исправить конфигурацию; та же failed revision не запускается повторно.

Проверки безопасности

Публичные annotations не являются полномочием. Защищенный state хранит полный intent, hash только его metadata, отмену и отметки выполнения. Перед patch повторно проверяются точный checkpoint, Secret UID, текущие проверенные bytes, revision, intent, CR/Store UID и generations, разрешенные Deployment и фактическая ссылка на Secret.

Учитываются envFrom, SecretKeyRef и смонтированные Secret/projected volumes в обычных и init-контейнерах. Неиспользуемый volume, label или imagePullSecret не считается использованием конфигурации. Patch содержит тесты UID/resourceVersion и меняет только собственную Pod-template annotation secrets.sekvyr.ru/restart-<SecretUID>. Образ, env, команды, replicas, strategy и чужие annotations сохраняются.

Внутренние Guard и Result скрывают проверенные значения при форматировании через String/GoString. Восстановление из отсутствующего state или поддельных markers не создает разрешение на restart.

Секреты и внутренние данные151 новый/измененный файл-кандидат проверен без исключений: подтвержденных секретов и внутренних данных нет. JSON, Python, HTML и все ссылки на артефакты проверены; внешних ресурсов HTML нет.

Проверены также подмена public revision/intent при нетронутом защищенном state, fork, поврежденные подпись/ciphertext, replay старого снимка, устаревший индекс панели, suspended CR, запрещенный Deployment, смена UID приложения, потеря/замена state и реальные RBAC-запреты. В завершающем отрицательном тесте Ready/DataCurrent стали false после намеренной замены state — это ожидаемый безопасный отказ.

В первом живом прогоне обнаружен установленный на стенде внешний Reloader: он независимо изменил тестовый Deployment. Такой прогон не принят как доказательство отсутствия лишних restart. Чистый повтор использует штатный opt-out только на своем Deployment — reloader.stakater.com/auto: "false"; общий контроллер не менялся. Это поддерживаемая аннотация Stakater Reloader.

Число rollout проверяется по новым ReplicaSet/Pod UID и точному изменению Pod template, а не по одному счетчику Deployment generation. В Kubernetes изменение Deployment annotations также может увеличивать generation; это видно в исходниках соответствующей версии.

Границы результата

Этап 5 не означает production readiness. Witness остается явным development filesystem профилем, без гарантии WORM и доказанной независимости production restore-domain. HA/fencing, ротации и полноценное восстановление остаются для этапа 6.

  • Нет общей транзакции между state, Secret, полномочиями и Deployment; гарантия exactly-once и мгновенный отзыв уже выполняющейся записи не заявляются. Неоднозначная частичная запись блокирует rollout и может требовать административного восстановления.
  • Debounce относится к одному binding/Secret. Одновременные изменения нескольких разных Secrets одного приложения не объединяются в одну транзакцию.
  • UID Deployment закрепляется для текущего контекста CR/Store generations и списка имен. Изменение generation считается новой административной авторизацией и может закрепить новый UID. Враждебный общий namespace не поддерживается.
  • Отложенный кандидат с еще не найденным UID может впервые закрепить разрешенное имя после восстановления доступа. Приложение, созданное после изменения Secret, при этом может получить дополнительный rollout; без доказательства момента чтения env эвристика по creationTimestamp не используется.
  • Нужно выбрать один контроллер перезапуска для приложения и этого Secret. Sekvyr не выключает чужие reloaders автоматически и не может подавить restart другого контроллера.
  • Поддержан только Deployment. Приложения со StatefulSet/DaemonSet, произвольные hooks и обновление рабочих Pod через delete/scale не входят в этап.
  • Изменения совместимости state с более старыми бинарниками, полноценные миграции, независимое security review и выпуск остаются отдельными этапами. Старый бинарник может отвергнуть новые state-поля.

Артефакты

После приемки удалены ресурсы всех трех удаленных тестовых запусков: 12 namespace, два тестовых CRD и связанные persistent volumes отсутствуют. Независимая проверка подтвердила Ready нод и штатных workloads; UID и spec штатных workloads совпадают с исходным снимком. Временные port-forward и отдельный процесс сборки остановлены. Сгенерированные private fixtures и копии административного kubeconfig удалены.
