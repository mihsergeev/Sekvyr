# Sekvyr в Kubernetes

[English version](README.md)

Ниже описаны существующий init/sidecar и ESO. Для нового оператора отдельно
читайте [установку и bootstrap](../../operator/docs/install.ru.html) и
[эксплуатацию, ротации и rollback](../../operator/docs/operations.ru.html).
Оператор имеет собственные CRD, административные UID pins и выключенный по
умолчанию rollout. Его E2E2 API требует отдельно рассмотренного unreleased
backend; опубликованный 1.0.3 задним числом не меняется.

Projected ServiceAccount token позволяет не хранить постоянную машинную пару
client id/secret. Сам JWT, выданная machine session и node key остаются
чувствительными данными: украденный bearer может использоваться до истечения
или применимого отзыва. Комментарии примеров о "нечего украсть" не являются
гарантией безопасности.

## 1. Без статических секретов: токен ServiceAccount

Под предъявляет свой projected-токен ServiceAccount, панель проверяет подпись по
ключам кластера и отдает разрешенные значения. Пример запрашивает токен на час
с audience панели и bound Pod claims. Панель проверяет offline JWKS и
сопоставляет namespace + имя ServiceAccount, без live TokenReview и без
регистрации SA UID. Удаление Pod не гарантирует немедленный отзыв такого JWT.
Отдельные UID pins нового оператора не меняют эту модель backend.

Один раз на кластер:

```sh
kubectl get --raw /openid/v1/jwks                    # public keys
kubectl get --raw /.well-known/openid-configuration  # public issuer metadata
```

В панели: "Серверы", меню "...", "Добавить кластер" (имя, `issuer`, `audience`,
ключи). Затем в том же меню "Личность в кластере" с этим кластером, namespace и
именем ServiceAccount, и выдача ей окружения: владелец панели делает это в
разделе "Доступ" (раздел видит только он), ответственный - кнопкой "Подключить
приложение" на ее странице в "Серверах".

Дальше [agent-sidecar.yaml](agent-sidecar.yaml): init-контейнер пишет файл до
старта приложения, спутник держит его свежим. В образе
`ghcr.io/mihsergeev/sekvyr-agent` тот же подписанный агент, что панель раздает
серверам. В поде он сам не обновляется (`--no-update`): выбирайте отдельно
проверенный image digest. Сверяйте YAML-пример перед применением; плавающий tag
не является воспроизводимым pin.

При успешной синхронизации с интервалом из примера правка обычно доезжает до
файла примерно за минуту; сетевой отказ не дает такого срока. Приложение видит
ее только после перечитывания. Проще всего читать файл по таймеру или по
inotify (файл заменяется целиком, поэтому следить нужно за каталогом
`/secrets`, а не за файлом). Сигнал из спутника требует большего: спутник
работает под uid 65534 без capabilities и не может слать сигналы процессу
другого пользователя. Сработает так: `shareProcessNamespace: true` у пода,
одинаковый `runAsUser` у спутника и приложения и
`--on-change "pkill -HUP -x app"` у спутника. Иначе перезапустите поды.

Legacy E2E1-проектам с шифрованием в браузере нужен ключ ноды, общий для всех
реплик: в
примере показано, как один раз завести его Secret'ом и указать на него
`SEKVYR_NODE_KEY`. Без общего ключа каждый под заводил бы свой, и ключ проекта,
запечатанный для одного, не открылся бы в остальных. Это не инструкция E2E2
bootstrap: опубликованный agent 1.0.3 проверен в этапе 7 без изменения
бинарника как Plain init/sidecar; E2E2-поддержка ему не приписывается.

Почему ключи кластера, а не TokenReview: панели не нужны ни учетные данные
кластера, ни доступ к его API. Плата - обновлять ключи, когда кластер их меняет:
"Серверы", таблица кластеров, "Обновить ключи". Личности подов и выданные им
права при этом остаются.

## 2. Через External Secrets Operator

Для тех, у кого ESO уже стоит: [external-secrets.yaml](external-secrets.yaml).
Панель отдает значения обычным запросом, ESO раскладывает их в `Secret`.

Плата - статическая пара "идентификатор + секрет" в `Secret` кластера: ESO ходит
одним запросом и не умеет сперва менять секрет на короткий токен. Секрет того же
рода, что лежал бы у любого другого провайдера ESO, и ездит он только по TLS, но
это именно то, чего первый путь не требует вовсе.

Каждый ключ - отдельный запрос. В журнал попадает новый набор значений, новый
адрес и раз в сутки, повторы между этим считаются, а не пишутся строкой каждый.

## Что машина может

В этом разделе речь о машинном API панели. Он дает только чтение значений.
В машинном контуре четыре маршрута, которые что-то меняют (token,
report, revoke, enroll), и ни один не касается значений. Захваченный под отдает
свои секреты, которые и так у него в памяти, но не портит общее хранилище и не
подменяет значения соседям. Новый оператор отдельно записывает Kubernetes
Secret и при явном opt-in патчит Deployment по своим RBAC/UID-гейтам;
ограничения machine API не означают read-only доступ оператора к Kubernetes.
